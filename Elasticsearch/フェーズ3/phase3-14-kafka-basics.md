## 14.1 Kafka はキューではない ― 「読んでも消えない」ということ

まず、多くの人が持っている「メッセージキュー」のイメージと比べます。

```
【従来のメッセージキュー（RabbitMQ など）】

  Producer --> [ ■ ■ ■ ] --> Consumer
                 キュー          |
                                 v
               取り出したメッセージは
               キューから消える

  → 「誰が処理したか」の管理はブローカーの仕事
  → もう一度読みたい？ 無理です。消えました


【Apache Kafka】

  Producer --追記--> [ ■ ■ ■ ■ ■ ■ ■ ■ ] ← ログファイル（消えない）
                       0 1 2 3 4 5 6 7
                             ^       ^
                             |       |
                       ConsumerA  ConsumerB
                       （3まで読んだ）（7まで読んだ）

  → メッセージは読まれても消えない。保持期間が来るまで残る
  → 「どこまで読んだか」は各Consumerが自分で覚える
  → 何度でも、何人でも、好きな位置から読める
```

この違いがすべてです。Kafka のメッセージは、読まれたからといって消えません。**設定した保持期間（デフォルトで7日など）が来るまで、ディスク上のファイルに残り続けます。**

だからこそ、第13章で挙げた性質が成立します。

| 第13章で挙げた理由 | Kafkaのどの性質から来るか |
|---|---|
| ①バッファ | 読まれなくてもディスクに溜め続けられる |
| ②リプレイ | 消えないので、読む位置を巻き戻せる |
| ③fan-out | 消えないので、複数の読み手が独立して読める |
| ④疎結合 | 読み手の状態がブローカーに影響しない |
| ⑤順序保証 | ログは追記専用なので、書いた順に並んでいる |

> 💡 **なぜログなのか**：第13章で「DBは変更をログに追記している」と学びました。Kafka は、その**追記ログという構造だけを取り出して、汎用のミドルウェアにしたもの**だと考えると理解しやすくなります。CDCと Kafka の相性が良いのは偶然ではなく、両者が同じデータ構造の上に立っているからです。

## 14.2 4つの基本概念

### トピック（topic）

メッセージの**分類名**です。DBでいうテーブルに相当します。今回のパイプラインでは `shop.shopdb.products` というトピックに商品の変更イベントが流れます。

### パーティション（partition）

トピックは1つ以上の**パーティション**に分割されます。**これがKafkaの並列処理の単位**です。

```
トピック: shop.shopdb.products （パーティション数 = 3）

 partition 0 : [ ■ ][ ■ ][ ■ ][ ■ ]        ← 独立したログファイル
                 0    1    2    3
 partition 1 : [ ■ ][ ■ ]
                 0    1
 partition 2 : [ ■ ][ ■ ][ ■ ]
                 0    1    2
```

重要な性質が2つあります。

1. **順序が保証されるのはパーティションの中だけ**。パーティションをまたいだ順序は保証されません
2. パーティション数がそのまま**並列に読める上限**になります

### オフセット（offset）

パーティション内での**通し番号**です。0から始まり、追記のたびに1ずつ増えます。上の図の `0 1 2 3` がそれです。

オフセットは「メッセージの住所」であり、同時に「どこまで読んだか」を表す**しおり**でもあります。「オフセット5から読み直す」と指定すれば、そこから再生できます。これが第13章の「リプレイ」の正体です。

### コンシューマグループ（consumer group）

同じ `group.id` を名乗るコンシューマの集まりです。**Kafkaは、1つのパーティションをグループ内の1人だけに割り当てます。**

```
トピック（3パーティション）
 ┌───────────┐
 │partition 0│──┐
 ├───────────┤  ├──> [グループ "es-sink"]
 │partition 1│──┤       consumer-1 : p0, p1 担当
 ├───────────┤  │       consumer-2 : p2 担当
 │partition 2│──┘
 │           │
 └─────┬─────┘
       │
       └──────────> [グループ "dwh-sink"]  ← 別グループは独立して全部読める
                       consumer-1 : p0,p1,p2 担当
```

- **同じグループ内**では、パーティションが分担される → **スケールアウト**
- **別のグループ**は互いに無関係に、同じデータを全部読める → **fan-out**

つまり「グループ内で分担、グループ間で複製」です。この2つを1つの仕組みで実現しているのがKafkaの巧みなところです。

> ⚠️ **コンシューマを増やしても速くならない場合がある**
> パーティションが3つしかないトピックに、同じグループのコンシューマを4つ起動しても、**4人目には何も割り当てられません**（待機状態になります）。並列度の上限はパーティション数で決まります。

## 14.3 メッセージキーとパーティションの決まり方

Kafkaのメッセージは **キー（key）** と **値（value）** のペアです。プロデューサーは、どのパーティションに送るかを次のように決めます。

```
  キーがある場合   →  hash(キー) % パーティション数  で決定
  キーがない場合   →  ほぼ均等に振り分け（ラウンドロビン等）
```

ここが決定的に重要です。

> **同じキーのメッセージは、必ず同じパーティションに入る。**
> **パーティション内では順序が保証される。**
> **⇒ 同じキーのメッセージは、書いた順に読まれることが保証される。**

CDCでは、**メッセージキーにテーブルの主キー（商品ID）を使います**。すると、

```
商品ID=1 の変更履歴 → 必ず partition 1（例）に、コミット順で並ぶ
   offset 10: 価格 98000 → 89000
   offset 25: 価格 89000 → 79000
   offset 40: 在庫 true → false

商品ID=2 の変更履歴 → 必ず partition 0 に、コミット順で並ぶ
```

これで、第13章の「罠②：並行更新で順序が逆転する」が**仕組みとして防がれます**。商品1と商品2の間の順序は保証されませんが、**そもそも別々の商品の更新順序はどうでもよい**のです。必要な順序だけを、安いコストで守る。これがキー設計の要点です。

> 💡 **コラム：パーティション数を後から増やしてはいけない（CDCでは特に）**
> パーティション数を3から6に増やすと、`hash(キー) % 3` だった計算が `hash(キー) % 6` に変わります。つまり **同じ商品IDのメッセージが、ある時点から別のパーティションに行き始めます**。
> 古いパーティションにはその商品の過去のイベントが残り、新しいパーティションには新しいイベントが入るため、**「古い更新が、新しい更新より後に読まれる」事故**が起こり得ます。CDC用トピックのパーティション数は、最初に余裕を持って決めてください（減らすことは、そもそもできません）。

## 14.4 ハンズオン ― Kafka を起動する

### 14.4.1 docker-compose.yml を更新する

付属の `phase3-14/docker-compose.yml` を、**フェーズ1 第4章で作った `Dockerfile` と同じフォルダ**に置いて（既存の compose を上書きして）ください。Elasticsearch と Kibana はそのまま、Kafka と Kafka UI が追加されています。

Kafka サービスの要点だけ抜き出します。

```yaml
  kafka:
    image: apache/kafka:4.1.2
    ports:
      - "29092:29092"
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller      # 1台で両方を兼任
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_LISTENERS: PLAINTEXT://:9092,PLAINTEXT_HOST://:29092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092,PLAINTEXT_HOST://localhost:29092
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1   # 1ノードなので必須
      ...
```

**つまずきポイントを3つ、先に潰しておきます。**

**① ZooKeeper が要らない**
ネット上の記事の多くには `zookeeper` サービスが書かれていますが、**Kafka 4.0 以降、ZooKeeper は完全に削除されました**。現在は **KRaft（Kafka Raft）モード**といって、Kafka自身がクラスタのメタデータ（どのブローカーが生きているか、パーティションのリーダーは誰か等）を管理します。`KAFKA_PROCESS_ROLES: broker,controller` は「この1台がデータ配信役とメタデータ管理役を兼任する」という宣言です。古いcompose設定をコピーしてくると起動しないので注意してください。

**② リスナーが2つある理由**
Kafkaは接続してきたクライアントに「私に接続するならこのアドレスを使え」と**教え返す**性質があります（`advertised.listeners`）。ここが1つだと、必ずどちらかが繋がりません。

| 呼ぶ場所 | 使うアドレス | 理由 |
|---|---|---|
| Dockerネットワーク内（Kafka Connect等） | `kafka:9092` | コンテナ名で名前解決できる |
| ホストPC（あなたの端末） | `localhost:29092` | ホストからは `kafka` という名前は引けない |

「なぜかホストからだけ繋がらない」というトラブルの9割はここが原因です。

**③ レプリケーションファクタは全部1にする**
Kafkaは内部トピック（オフセット管理用など）を既定でレプリカ3で作ろうとしますが、**1ノードしかないので失敗します**。`..._REPLICATION_FACTOR: 1` の各行はそのための指定です。

### 14.4.2 起動と確認

```bash
docker compose up -d --build
docker compose ps
```

Kafkaに疎通できるか確認します。以降、Kafkaのコマンドは**コンテナの中**で実行します（`/opt/kafka/bin/` にあります）。

```bash
docker compose exec kafka /opt/kafka/bin/kafka-broker-api-versions.sh \
  --bootstrap-server localhost:9092 | head -n 3
```

ブローカーの情報が返ってくれば成功です。

> 毎回長いので、シェルのエイリアスを切っておくと快適です。
> ```bash
> alias kf='docker compose exec kafka /opt/kafka/bin'
> ```
> ※ 実際にはエイリアスにパスは含められないので、以降は長い形のまま記載します。

## 14.5 ハンズオン ― トピックを作り、送受信する

### トピックの作成

```bash
docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic lesson \
  --partitions 3 --replication-factor 1
```

### 中身を確認

```bash
docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --topic lesson
```

```
Topic: lesson  PartitionCount: 3  ReplicationFactor: 1  Configs: ...
   Topic: lesson  Partition: 0  Leader: 1  Replicas: 1  Isr: 1
   Topic: lesson  Partition: 1  Leader: 1  Replicas: 1  Isr: 1
   Topic: lesson  Partition: 2  Leader: 1  Replicas: 1  Isr: 1
```

3つのパーティションができています。14.2の図がそのまま現実になりました。

### メッセージを送る（キー付き）

ターミナルを1つ開き、プロデューサーを起動します。

```bash
docker compose exec -it kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 \
  --topic lesson \
  --property parse.key=true \
  --property key.separator=:
```

プロンプト（`>`）が出たら、`キー:値` の形式で入力します。**商品IDをキーに見立てて**送ってみましょう。

```
>1:ノートPC 98000円
>2:ワイヤレスマウス 3200円
>1:ノートPC 89000円     ← 商品1の値下げ
>3:USBハブ 2400円
>1:ノートPC 79000円     ← 商品1のさらなる値下げ
```

`Ctrl+C` で抜けます。

### メッセージを読む（最初から）

別のターミナルで、コンシューマを起動します。

```bash
docker compose exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic lesson \
  --from-beginning \
  --property print.key=true \
  --property print.partition=true \
  --property print.offset=true
```

出力例（並び順は環境により異なります）：

```
Partition:1  Offset:0  1  ノートPC 98000円
Partition:1  Offset:1  1  ノートPC 89000円
Partition:1  Offset:2  1  ノートPC 79000円
Partition:0  Offset:0  2  ワイヤレスマウス 3200円
Partition:2  Offset:0  3  USBハブ 2400円
```

**ここで確認してほしいこと**が2つあります。

1. **キー `1` のメッセージは、すべて同じパーティションに、送った順（offset 0→1→2）で入っている**。14.3で学んだキーとパーティションの関係が、目に見える形で確認できました
2. キーが違えば別のパーティションに散っている

### 「消えない」ことを確認する

コンシューマを `Ctrl+C` で止め、**もう一度まったく同じコマンドを実行**してください。

```
→ 同じメッセージが、また最初から全部流れてくる
```

これが `--from-beginning` の効果であり、**Kafkaが「読んでも消えない」ことの実演**です。第13章の「リプレイ」は、まさにこの操作を本番規模で行うことに他なりません。

## 14.6 ハンズオン ― コンシューマグループとラグ

`--from-beginning` は「毎回最初から」でしたが、実際のアプリは「前回の続き」から読みたいはずです。それがコンシューマグループの役目です。

### グループを指定して読む

```bash
docker compose exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic lesson \
  --group my-app \
  --from-beginning \
  --property print.key=true
```

全部読んだら `Ctrl+C` で止め、**`--from-beginning` を外して**同じコマンドを実行します。

```bash
docker compose exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic lesson \
  --group my-app \
  --property print.key=true
```

→ **何も表示されません。** グループ `my-app` は「もう全部読んだ」という位置（オフセット）を記憶しているからです。

この状態のまま、別ターミナルからプロデューサーで新しいメッセージを1件送ってみてください。**そのメッセージだけが表示される**はずです。

> 📌 **オフセットはどこに保存されているのか**
> `__consumer_offsets` という Kafka 内部のトピックです。つまり「どこまで読んだか」もまた、Kafkaのログとして記録されています。コンシューマ側のディスクやDBに状態を持たないため、**コンシューマを別のマシンで起動し直しても続きから読める**わけです。

### コンシューマラグを見る

運用でいちばんよく使うコマンドがこれです。

```bash
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --describe --group my-app
```

```
GROUP   TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID
my-app  lesson  0          1               1               0    -
my-app  lesson  1          3               5               2    -
my-app  lesson  2          1               1               0    -
```

- **CURRENT-OFFSET**：このグループが読み終わった位置
- **LOG-END-OFFSET**：トピックに書き込まれている最新位置
- **LAG**：その差＝**まだ処理できていない件数**

**LAG が増え続けているかどうかが、CDCパイプラインの健康診断そのものです。** 第16章以降、「Elasticsearchへの反映が遅れている」と感じたら、まずこのコマンドで「Kafkaに届いていないのか（Debezium側の問題）／Kafkaにはあるが取り込めていないのか（シンク側の問題）」を切り分けます。

### オフセットを巻き戻す（リプレイ）

```bash
# コンシューマを止めた状態で実行すること
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --group my-app --topic lesson \
  --reset-offsets --to-earliest --execute
```

これで `my-app` は「まだ何も読んでいない」状態に戻ります。もう一度コンシューマを起動すると、全メッセージが再び流れてきます。

> ⚠️ グループにアクティブなコンシューマがいるとリセットは拒否されます。必ず止めてから実行してください。第17章で「ESのマッピングを変えたので全イベントを流し直す」ときに、この操作が主役になります。

## 14.7 保持期間とログコンパクション ― CDCの隠れた主役

「消えない」と言ってきましたが、無限に貯めることはできません。Kafkaには2種類の掃除方式があります。

### 方式A：`cleanup.policy=delete`（既定）

**時間または容量で、古いものから捨てます。**

| 設定 | 意味 | 既定値 |
|---|---|---|
| `retention.ms` | 何ミリ秒保持するか | 604800000（7日） |
| `retention.bytes` | パーティションごとの上限バイト数 | -1（無制限） |

ログの「古い側」から順に削除されます。

### 方式B：`cleanup.policy=compact`（ログコンパクション）

**キーごとに、最新の1件だけを残します。** 時間ではなく「同じキーの古い版」を消す方式です。

```
【コンパクション前】
 key=1: 98000 │ key=2: 3200 │ key=1: 89000 │ key=3: 2400 │ key=1: 79000
 offset 0        offset 1       offset 2       offset 3      offset 4

                    ↓ コンパクション

【コンパクション後】
                  key=2: 3200 │ key=3: 2400 │ key=1: 79000
                  offset 1       offset 3      offset 4
```

**これがCDCで効いてきます。** 商品1が過去に100回値下げされていても、`key=1` の最新の1件さえあれば「今の商品1の姿」は復元できます。つまり、

> **コンパクトされたトピックは、テーブルの「スナップショット」として使える。**

新しくコンシューマを追加したとき、全履歴を読まなくても、コンパクト済みトピックを頭から読むだけで**現在の全商品の状態を再構築できる**わけです。Debezium が使う内部トピック（スキーマ履歴やオフセット保存用）も、この方式で作られます。

### tombstone の正体

ここで第13章の「論点2：削除」が回収されます。コンパクションの世界では、

> **キーはあるが値が `null` のメッセージ ＝ 「このキーはもう存在しない」という宣言**

です。これを **tombstone（墓石）** と呼びます。コンパクションはこのメッセージを見て、そのキーの過去の全メッセージを削除します（tombstone自体も一定時間後に消えます）。

Debezium が削除時に tombstone を出すのは、この Kafka の作法に従っているからです。そして第16章では、Elasticsearch シンクコネクタに「**tombstone を受け取ったらドキュメントを削除せよ**」と教える設定を行います。

```
MySQL: DELETE FROM products WHERE id=3
   ↓
Kafka: key=3, value={op:"d", before:{...}}   ← 削除イベント
       key=3, value=null                     ← tombstone
   ↓
ES:    DELETE /products/_doc/3
```

一本の線でつながりました。

> 💡 **コラム：コンパクションはすぐには起こらない**
> 手元で試すと「消えないぞ？」となりますが、それは正常です。コンパクションは**アクティブなセグメント（今書き込み中のファイル）には適用されず**、`segment.ms` や `min.cleanable.dirty.ratio` の条件を満たしてから、バックグラウンドで動きます。学習で挙動を見たい場合は、トピック作成時に `--config segment.ms=10000 --config min.cleanable.dirty.ratio=0.001` のような極端な値を付けてください。**本番でこの設定をしてはいけません**（小さなファイルが大量にできます）。

## 14.8 Kafka Connect ― 次章への橋

ここまで、メッセージの送受信をCLIで行いました。しかし本番のパイプラインで「MySQLからKafkaへ」「KafkaからESへ」を運ぶプログラムを自分で書くのは大変です。エラー処理、リトライ、オフセット管理、並列化、監視……。

そこで使うのが **Kafka Connect** です。

```
     [ Kafka Connect ワーカー（プロセス） ]
        │
        ├── ソースコネクタ  : 外部システム → Kafka   （例：Debezium MySQL）
        └── シンクコネクタ  : Kafka → 外部システム   （例：Elasticsearch）

     設定は REST API に JSON をPOSTするだけ。コードは書かない。
```

Kafka Connect は「コネクタを動かすための共通ランタイム」で、上記の面倒ごとを全部引き受けてくれます。私たちがやるのは、**設定JSONを書いてPOSTすること**だけです。

次章では、この Kafka Connect を起動し、Debezium MySQL コネクタを登録して、**MySQLのUPDATEがKafkaトピックに流れてくる瞬間**を目で見ます。

---

## まとめ

- Kafka は**キューではなく、追記専用の分散コミットログ**である。メッセージは読まれても消えず、保持期間まで残る。第13章で挙げたKafkaを挟む5つの理由は、すべてこの性質から導かれる
- **トピック**は分類、**パーティション**は並列と順序の単位、**オフセット**はパーティション内の通し番号、**コンシューマグループ**は「グループ内で分担・グループ間で複製」を実現する仕組み
- **順序が保証されるのはパーティション内だけ**。同じキーは同じパーティションに入るため、**メッセージキーに主キーを使えば、その行の変更順序が保証される**
- パーティション数を後から増やすと、同じキーの行き先が変わり、CDCでは順序事故の原因になる
- Kafka 4.x では **ZooKeeper は廃止され、KRaftモード**のみ。1ノード構成ではレプリケーションファクタを明示的に1にする必要がある。リスナーは「コンテナ内から」「ホストから」の2系統を用意する
- **コンシューマラグ**（`kafka-consumer-groups.sh --describe`）は、パイプラインの詰まりを切り分ける最重要コマンド
- 掃除方式には `delete`（時間・容量で古いものを削除）と `compact`（キーごとに最新のみ残す）がある。**コンパクトされたトピックはテーブルのスナップショットとして機能し、値が `null` の tombstone が「削除」を意味する**

## 理解度チェック

**問1.** Kafkaと従来のメッセージキューの、最も本質的な違いを述べてください。またその違いが、CDCパイプラインにどんな利点をもたらしますか。

**問2.** 3つのパーティションを持つトピックに、同じコンシューマグループのコンシューマを5つ起動しました。何が起こりますか。

**問3.** CDCで、メッセージキーにテーブルの主キーを使うのはなぜですか。もしキーを付けずに（`null` キーで）送った場合、何が起きるでしょうか。

**問4.** `kafka-consumer-groups.sh --describe` の出力で、`LAG` が時間とともに増え続けています。これは何を意味し、どう切り分けますか。

**問5.** `cleanup.policy=compact` のトピックに、次の順でメッセージが書かれました。コンパクション後に残るのはどれですか。また、その結果からわかる「コンパクト済みトピックの使い道」を述べてください。

```
key=A: v1 / key=B: v1 / key=A: v2 / key=C: v1 / key=B: null / key=A: v3
```

<details>
<summary>解答を見る</summary>

**問1.**
従来のキューは**読み取ると消える**のに対し、Kafkaは**読まれてもメッセージが残り、各コンシューマが自分の読み取り位置（オフセット）を持つ**点。
CDCへの利点：
- ES側が停止していてもイベントを溜めておける（バッファ）
- オフセットを巻き戻して過去のイベントを再処理できる（リプレイ）
- 同じイベントを検索・分析・キャッシュなど複数の用途に配れる（fan-out）

**問2.**
パーティションは1グループ内で1コンシューマにしか割り当てられないため、**3つのコンシューマだけが担当を持ち、残り2つは何も割り当てられず待機状態になる**。コンシューマを増やしても並列度はパーティション数（3）を超えられない。

**問3.**
プロデューサーは `hash(キー) % パーティション数` で送り先を決めるため、**主キーをキーにすれば同じ行の変更イベントが必ず同じパーティションに入り、パーティション内の順序保証によってコミット順で処理される**から。
キーを付けない場合、同じ商品の変更イベントが複数のパーティションに散らばる。パーティション間の順序は保証されないため、**古い更新が新しい更新の後に処理され、Elasticsearchに古い値が残る**危険がある。加えて、ログコンパクションも機能しない（キーがないため最新1件を選べない）。

**問4.**
コンシューマ（＝ESシンクコネクタなど）の**処理速度が、書き込み速度に追いついていない**ことを意味する。放置すると反映遅延が拡大し、保持期間を超えると未処理のままメッセージが削除される恐れもある。
切り分け：
- そもそもKafkaにイベントが届いているか（LOG-END-OFFSETが伸びているか）→ 伸びていなければ上流（Debezium／MySQL）側の問題
- 届いているのにCURRENT-OFFSETが進まない → 下流（シンクコネクタ／Elasticsearch）側の問題。コネクタのエラー、ESの書き込み拒否、並列度不足などを疑う

**問5.**
残るのは **`key=C: v1` と `key=A: v3`**。
- A は最新の `v3` のみ残る
- B は最後が `null`（tombstone）なので、Bのメッセージはすべて削除される
- C は1件だけなのでそのまま残る

使い道：**キーごとの「現在の状態」だけが残るため、テーブルのスナップショットとして扱える。** 新しいコンシューマは全履歴を読まなくても、このトピックを頭から読むだけで現在の全レコードの状態を復元できる。またCDCにおいては、値が `null` のメッセージ（tombstone）が「そのキーの行は削除された」という意味を持つ。

</details>
