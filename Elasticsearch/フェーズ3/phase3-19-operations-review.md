# 第19章　運用と総合演習 ― 監視・障害対応・本番化チェックリスト

> Elasticsearch学習教科書 ― フェーズ3「CDCパイプライン構築」最終章
> 前提知識：第13〜18章

パイプラインは動きました。しかし CDC の本当の難しさは、**作ることではなく、動き続けさせること**にあります。

CDCパイプラインには、他のシステムにない厄介な性質があります。**壊れても、しばらく誰も気づかない**のです。検索結果は返ってきます。エラーも出ません。ただ、データが少しずつ古くなっていく。気づくのは、ユーザーからの「在庫があるって書いてあったのに」という問い合わせです。

だからこの章は、**「気づける状態にする」** ことから始めます。

---

## この章で学ぶこと（学習目標）

- CDCパイプラインの**4つの観測点**を挙げ、それぞれで何を見るべきか説明できる
- 「気づかないうちにズレる」ことを防ぐ**整合性チェック**の考え方を持てる
- 代表的な障害に対して、切り分けの順序と復旧手順を実行できる
- 学習用構成を本番に持っていく際の**チェックリスト**を説明できる
- フェーズ1〜3で学んだことを、1つのシナリオの中で統合して考えられる

## 19.1 4つの観測点

パイプラインは4区間に分かれます。**どこで詰まっているかを機械的に切り分けられる**ようにしておくのが、監視設計の目的です。

```
  [MySQL] ──①──► [Debezium] ──②──► [Kafka] ──③──► [Logstash/Sink] ──④──► [ES]
```

### ① MySQL側：binlog は出ているか、消えていないか

| 見るもの | 確認方法 | 異常の兆候 |
|---|---|---|
| binlogの現在位置 | `SHOW BINARY LOG STATUS`（8.4〜。8.0までは `SHOW MASTER STATUS`） | 更新しても位置が動かない |
| binlogの保持 | `SHOW BINARY LOGS;` とディスク使用量 | ディスク逼迫、あるいは**逆に**古いログが消えすぎ |
| レプリカ接続 | `SHOW REPLICAS;` | Debezium が一覧に出てこない＝切断 |

**最も怖いのが「消えすぎ」です。** 第13章で触れたとおり、Debezium が止まっている間に未読の binlog がパージされると、**追従不能になり全件やり直し**になります。`binlog_expire_logs_seconds` は、想定される最大停止時間より十分長く設定してください。

### ② Debezium：遅れていないか

```bash
curl -s localhost:8083/connectors/products-source/status | jq '.connector.state, .tasks[].state'
```

状態は5種類あります。

| 状態 | 意味 |
|---|---|
| `RUNNING` | 正常 |
| `PAUSED` | 意図的に停止中 |
| `FAILED` | **異常**。`trace` を読む |
| `UNASSIGNED` | ワーカーに割り当てられていない |
| `RESTARTING` | 再起動中 |

さらに重要なのが **JMXメトリクス**です。Debezium が公開するもののうち、運用でいちばん見るのは1つです。

```
 debezium.mysql:type=connector-metrics,context=streaming,server=shop
   ├── MilliSecondsBehindSource   ← ★ DBのコミットから何ミリ秒遅れているか
   ├── NumberOfCommittedTransactions
   └── QueueTotalCapacity / QueueRemainingCapacity
```

**`MilliSecondsBehindSource` が増え続けていたら、CDCが追いつけていない**という直接的な証拠になります。これをPrometheus等で収集し、閾値アラートを張るのが定石です。

### ③ Kafka：溜まっていないか

第14章のコマンドがそのまま監視項目です。

```bash
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --all-groups
```

| 見るもの | 異常の兆候 |
|---|---|
| 各グループの `LAG` | 増え続けている＝下流が追いつけていない |
| `LOG-END-OFFSET` | 伸びない＝**上流**が止まっている |
| DLQトピックの件数 | 1件でも増えたら**必ず調査**（第16章） |

> 📌 **LAGとLOG-END-OFFSETを両方見ることに意味があります。**
> - LAGが増え、LOG-END-OFFSETも伸びている → 下流が遅い（シンクを疑う）
> - LAGは0だが、LOG-END-OFFSETが伸びない → 上流が止まっている（Debeziumを疑う）
> この2つの組み合わせだけで、切り分けの半分が終わります。

### ④ Elasticsearch：書き込めているか

```bash
curl -s "localhost:9200/_cluster/health?pretty"
curl -s "localhost:9200/_cat/thread_pool/write?v&h=node_name,active,queue,rejected"
curl -s "localhost:9200/_cat/indices/products*?v"
```

`rejected` が増えているのは、書き込みが速すぎてESが処理しきれていない証拠です。シンク側のバッチサイズを調整するか、ES側のリソースを増やします。

### そして最後に ― 整合性チェック

**これが最も重要で、最も忘れられます。** 上の4つはすべて「パイプラインの調子」を見ているだけで、**「データが正しいか」を見ていません**。

```bash
# 件数の照合（毎日でも数分ごとでもよい）
docker compose exec mysql mysql -uroot -prootpw shopdb -N -B \
  -e "SELECT COUNT(*) FROM products;"
curl -s "localhost:9200/products/_count" | jq '.count'
```

件数が一致しないなら、どこかで取りこぼしています。より丁寧にやるなら、

- **サンプリング比較**：ランダムに数十件のIDを選び、DBとESの内容を突き合わせる
- **チェックサム比較**：`updated_at` の最大値や、価格の合計値をDBとESの集計で比べる

そして、ズレが見つかったときの回復手段は第17章で学んだ**増分スナップショット**です。「ズレたら直せる」という仕組みを持っていることが、CDC運用の安心感の源になります。

> 💡 **コラム：CDCは「壊れないシステム」ではなく「直せるシステム」として設計する**
> 分散システムである以上、どこかで必ず不整合は起きます。重要なのは、①**気づける**（整合性チェック）、②**直せる**（再同期）、③**直しても止まらない**（エイリアス切替）の3点セットを最初から用意しておくことです。逆にこれさえあれば、多少の不具合は運用でカバーできます。

## 19.2 障害プレイブック

| 症状 | よくある原因 | 対処 |
|---|---|---|
| ESの件数がDBより少ない | シンクのエラー、DLQ行き | DLQを確認。原因を直して再投入、または `_update_by_query` / 増分スナップショット |
| ESに削除済み商品が残る | `delete.tombstone.handling.mode` が `drop` | 設定を直し、該当ドキュメントを手動削除 or 再構築（第16章） |
| 商品が重複する | `_id` が自動採番になっている | `document_id` / `key.ignore=false` を確認。インデックスを作り直す（第16章） |
| 更新が古い値に戻る | 順序の逆転 | 外部バージョニングを導入（第17章） |
| コネクタが `FAILED` | 権限・接続・スキーマ履歴 | `status` の `trace` → 原因を除去 → `POST .../tasks/0/restart` |
| `binlog is not available` | binlogがパージされた | **追従不能**。新しい `topic.prefix` で作り直し（第17章 レベル3） |
| 特定フィールドだけ入らない | マッピングが `dynamic:false` で未定義 | `PUT /_mapping` で追加 → `_update_by_query` |
| 日付が1970年になる | `DATE` 型の未変換 | パイプラインで日数→日付に変換（第17章） |
| LAGだけ増える | シンクが遅い／落ちている | シンクのログ、ESの `rejected`、バッチサイズを確認 |
| 全体が止まった | Kafka / ES / Connect のどれか | 下の切り分け手順へ |

### 切り分けの型

**必ず上流から順に**見ます。下流から見ると、上流の問題を下流の問題と誤診します。

```
 START
   │
   ├─ MySQLで更新できるか？ ────── No ──► DB自体の障害。CDCの話ではない
   │        Yes
   ├─ binlogのPositionは進むか？ ── No ──► binlog設定を確認（log_bin等）
   │        Yes
   ├─ コネクタは RUNNING か？ ───── No ──► status の trace を読む
   │        Yes
   ├─ トピックのLOG-END-OFFSETは
   │  伸びているか？ ────────────── No ──► Debezium側（接続・権限・遅延）
   │        Yes
   ├─ コンシューマのLAGは0か？ ──── No ──► シンク側（Logstash/Connectのログ）
   │        Yes
   └─ ESにドキュメントがあるか？ ── No ──► インデックス名・エイリアス・
            Yes                            マッピング・パイプラインを確認
             │
             └──► データは届いている。検索クエリ側の問題を疑う
```

## 19.3 本番化チェックリスト

本教科書の環境は、学習のために意図的に多くを省いています。**そのまま本番に持っていってはいけません。** 何を戻すべきかを整理します。

### セキュリティ

- [ ] `xpack.security.enabled=true` に戻す。ESのユーザー・ロールを作り、**最小権限**（`create_index`, `read`, `write`, `view_index_metadata` 程度）を付与する
- [ ] ES / Kafka / MySQL すべての通信を **TLS** 化する
- [ ] MySQL の CDC ユーザーは、対象DBに絞った権限にする
- [ ] パスワードを設定JSONに直書きしない。Kafka Connect の **ConfigProvider**（外部ファイルや環境変数からの読み込み）を使う
- [ ] Kafka に認証・認可（SASL / ACL）を設定する。特に**トピックの削除権限**は絞る

### 可用性

- [ ] Elasticsearch を複数ノード構成にし、`number_of_replicas` を1以上にする（学習用は0にしていた）
- [ ] Kafka を3ブローカー以上にし、CDCトピックは `replication.factor=3`、`min.insync.replicas=2`
- [ ] Kafka Connect を**分散モードで複数ワーカー**にする（1台落ちてもコネクタが引き継がれる）
- [ ] Logstash / シンクを冗長化する（コンシューマグループなので、増やせば自動で分担される）

### データ保護

- [ ] `binlog_expire_logs_seconds` を、想定される最大停止時間より十分長く
- [ ] **スキーマ履歴トピックのバックアップ**（消えると再スナップショットが必要）
- [ ] Elasticsearch の**スナップショット**（`_snapshot`）を定期取得
- [ ] インデックスは**必ずエイリアス経由**でアクセスさせる（第17章）

### 性能・設計

- [ ] CDCトピックの**パーティション数を最初に決めきる**（後から増やすと順序が壊れる：第14章）
- [ ] メッセージ形式を **Avro + Schema Registry** にする（JSONは冗長で、型情報も失われる）
- [ ] シンクのバッチサイズとESの `refresh_interval` を調整する（大量投入時は `refresh_interval` を延ばす）
- [ ] `dynamic: strict` にするか、未知フィールドの監視を入れる（第17章）

### 監視

- [ ] `MilliSecondsBehindSource`、コンシューマLAG、DLQ件数、コネクタstate にアラート
- [ ] **DB件数とES件数の定期照合**（これが最後の砦）
- [ ] 復旧手順（増分スナップショット、エイリアス切替）を**手順書にして、実際に一度試しておく**

## 19.4 総合演習

これまでの全19章を横断する問題です。実務で実際に起きる形にしてあります。

---

**演習1：検索結果に幽霊が出る**

ECサイトの運用担当から「販売終了した商品が検索結果に出続けている」と報告がありました。調べると、その商品はMySQLの `products` テーブルからは確かに削除されています。パイプラインの他の部分（新商品の追加、価格の更新）は正常に反映されています。

(a) 原因として最も可能性が高いものを挙げてください。
(b) どのコマンドで確認しますか。
(c) 恒久対策と、いま残っている不要ドキュメントの後始末を述べてください。

---

**演習2：値下げが反映されない**

深夜バッチで全商品の価格を更新したところ、翌朝には反映されていました。しかし「昨日ESのマッピングを直すために、Logstashのオフセットを巻き戻して再取り込みした」直後から、**一部の商品の価格が数日前の値に戻っている**ことが判明しました。

(a) 何が起きたのか説明してください。
(b) 再発防止策を、具体的な設定名を挙げて述べてください。
(c) その設定を入れると、ログに大量のエラーが出るようになります。なぜですか。どうしますか。

---

**演習3：カテゴリ名の変更が半分しか反映されない**

マーケティング部が `categories` テーブルのカテゴリ名を変更しました。カテゴリ一覧画面（`categories` インデックスを参照）はすぐ新しい名前になりましたが、商品検索のファセットには**古い名前と新しい名前が混在**しています。

(a) なぜ混在するのですか。
(b) 正しく反映させる手順を述べてください。
(c) 今後この作業を自動化する方法を1つ挙げてください。

---

**演習4：アナライザーを変えたい**

「ユーザーが『ノートパソコン』で検索しても『ノートPC』の商品が出ない」という課題を解決するため、シノニム辞書を更新することになりました。対象インデックスには10万件の商品があり、サービスは24時間稼働しています。

(a) 既存の `products` インデックスの設定を直接更新できますか。
(b) 検索を止めずに切り替える手順を、順を追って述べてください。
(c) 新インデックスにデータを流し込む方法を2つ挙げ、それぞれが使える条件を述べてください。

---

<details>
<summary>解答を見る</summary>

**演習1**

(a) **`delete.tombstone.handling.mode` の設定漏れ**（既定の `drop` のまま）。追加・更新は反映されるのに削除だけ反映されない、という症状はこれが典型。
（他の可能性：Kafka Connect ESシンクを使っている場合の `behavior.on.null.values` が既定のまま。あるいはアプリが論理削除に切り替えており、そもそもDELETEが発生していない）

(b)
```bash
# 1. 削除イベントがKafkaに流れているか
kafka-console-consumer.sh --topic shop.shopdb.products --from-beginning \
  --property print.key=true | grep '__deleted'
# 2. コネクタの現在の設定
curl -s localhost:8083/connectors/products-source/config | jq
# 3. ESに残っているか
curl -s "localhost:9200/products/_doc/{id}"
```

(c)
- 恒久対策：`transforms.unwrap.delete.tombstone.handling.mode` を（Logstash経路なら）`rewrite` に設定し、シンク側で `__deleted == "true"` を `action => "delete"` に振り分ける
- 後始末：設定変更後、Kafkaに削除イベントが残っていればオフセットを巻き戻して再適用する（第17章レベル1）。残っていない場合は、DBに存在するIDの一覧を取得し、ESにあってDBにないドキュメントを `_delete_by_query` で消す（またはインデックスを作り直す）

---

**演習2**

(a) **順序の逆転**。オフセットを巻き戻したことで、すでに反映済みの新しい価格の上に、**古いイベントが後から上書き**された。`_id` に主キーを使う冪等性は「同じイベントの重複」は防ぐが、「古いイベントの後追い適用」は防げない（第17章 17.1）。

(b) **外部バージョニング**を導入する。Logstash の output に
```
version      => "%{[@metadata][version]}"   # __source_ts_ms を渡す
version_type => "external_gte"
```
を設定する（Kafka Connect ESシンクなら相当する外部バージョン設定）。ESが「現在の版より古い書き込み」を拒否するようになる。
バージョン値は Debezium の `source.ts_ms` を `add.fields` で持ってきて使う。`external` ではなく `external_gte` を選ぶのは、同一ミリ秒内の更新が取りこぼされないようにするため。

(c) 古いイベントが拒否されるたびに **409 `version_conflict_engine_exception`** が発生するため。これは**設計どおりの正常動作**なので、`silence_errors_in_log => ["version_conflict_engine_exception"]` でログを抑制する。ただし「本当に異常な衝突」まで見えなくなるので、件数自体はメトリクスとして監視しておくとよい。

---

**演習3**

(a) 2つの理由が重なっている。
1. 商品ドキュメントの `category_name` は**カテゴリ名をコピーして持っている（非正規化）** ため、カテゴリ側を更新しても自動では変わらない
2. enrich プロセッサは、ポリシー実行時点の**スナップショット**を参照しており、`categories` インデックスをその場で見ているわけではない
「混在」しているのは、変更後に何らかの理由で再インデックスされた商品（＝CDCで別の更新が入った商品）だけが新しい名前になったため。

(b)
```bash
# 1. enrichのスナップショットを作り直す
curl -X POST "localhost:9200/_enrich/policy/category-lookup/_execute?wait_for_completion=true"
# 2. 影響を受ける商品だけを再インデックス
curl -X POST "localhost:9200/products/_update_by_query?pipeline=products-enrich&conflicts=proceed&refresh" \
  -H 'Content-Type: application/json' \
  -d '{"query":{"term":{"category":"pc"}}}'
```
`?pipeline=` の明示と、`conflicts=proceed`（CDCと併走するため）を忘れないこと。

(c) 以下のいずれか。
- `shop.shopdb.categories` トピックを購読する小さなアプリを作り、カテゴリ変更を検知したら上記2コマンドを自動実行する
- 定期ジョブ（例：10分ごと）でポリシー再実行＋`_update_by_query` を回す
- **Outbox パターン**に移行し、カテゴリ名変更時にアプリが該当商品のイベントを再発行する（第18章 18.6）

---

**演習4**

(a) **できません。** 既存フィールドのアナライザー（および `text` などの型）は、インデックス作成後に変更できません。シノニム辞書もアナライザー定義の一部なので、インデックスを作り直す必要があります。
（`synonym_graph` を `updateable: true` にして `_reload_search_analyzers` を使う方法もありますが、検索時アナライザーに限られ、事前の設計が必要です）

(b)
1. 新しいシノニム設定を含む `products_v4` を作成する（マッピングは既存と同じ＋辞書だけ更新）
2. データを流し込む（(c)参照）
3. 件数を照合し、代表的な検索クエリで結果を検証する
4. `POST /_aliases` で `remove: {index: products_v3, alias: products}` と `add: {index: products_v4, alias: products}` を**1リクエストにまとめて**実行（アトミック切替、無停止）
5. 問題があればエイリアスを v3 に戻すだけでロールバック
6. 安定を確認したら v3 を削除する

(c)
- **方法1：`_reindex`**（`products_v3` → `products_v4`）
  使える条件：**マッピング／アナライザーだけを変える**場合。既存データの内容は正しい前提。最も速く、上流に負荷をかけない。※ enrich を通したい場合は `_reindex` に `dest.pipeline` を指定する
- **方法2：Kafka からの再取り込み**（新しい `group_id` のシンクを立て、オフセットを先頭から読む）
  使える条件：必要な期間のイベントが Kafka の**保持期間内に残っている**こと。パイプラインの変換ロジック自体を変えた場合はこちらが必要
- （どちらも使えない場合＝第17章レベル3：Debeziumの**増分スナップショット**でDBから読み直す）

</details>

## 19.5 フェーズ3のまとめ

| 章 | 学んだこと | 核心 |
|---|---|---|
| 13 | CDCの設計思想 | 二重書き込みは壊れる。ログベースCDCがなぜ強いか |
| 14 | Kafkaの基礎 | Kafkaはキューではなくログ。キー＝順序保証の単位 |
| 15 | Debezium × MySQL | binlogをレプリカとして読む。スキーマ履歴と初期スナップショット |
| 16 | Kafka → Elasticsearch | `_id` に主キー＝冪等性。tombstoneで削除を伝える |
| 17 | スキーマ変更・順序・再同期 | 外部バージョニングとエイリアス切替。3レベルの再同期 |
| 18 | 非正規化 | fan-outとの戦い。enrichとOutboxパターン |
| 19 | 運用 | 気づける・直せる・止まらない、の3点セット |

そして、フェーズ全体を1行でまとめるなら、こうなります。

> **フェーズ1で「検索を動かし」、フェーズ2で「検索を賢くし」、フェーズ3で「検索を生かし続ける」仕組みを作った。**

第1章で `LIKE '%猫%'` の遅さから始まった旅は、転置インデックス、日本語形態素解析、スコアリング、シノニム、集計、ベクトル検索を経て、いま **「データベースの変更が1秒以内に検索結果へ反映されるパイプライン」** に到達しました。

## 19.6 この先へ

学び続けるための方向を、3つ挙げておきます。

**① ストリーム処理を深める**
第18章で名前だけ出した **Kafka Streams / Apache Flink** は、複数トピックのJOIN、時間窓の集計、状態を持った処理を可能にします。非正規化を本格的にやるなら、次はここです。

**② Elasticsearch の運用を深める**
シャード設計、**ILM（Index Lifecycle Management）** によるインデックスの世代管理、スナップショットと復旧、クラスタのスケーリング、そしてフェーズ2で最小構成に留めた **ベクトル検索・セマンティック検索の本番運用**（推論エンドポイント、ELSER、ハイブリッド検索のチューニング）。

**③ 検索そのものの品質を測る**
検索は「動く」だけでは価値になりません。クリックログの収集、**NDCG / MRR** といった評価指標、A/Bテスト、Learning to Rank。フェーズ2で学んだ `function_score` を、**勘ではなくデータで**調整できるようになる段階です。
