# 第13章　なぜCDCなのか ― 検索インデックスを「常に最新」に保つ設計

> **フェーズ3「CDCパイプライン構築」スタート**
> フェーズ1では検索を動かし、フェーズ2では検索の質を上げてきました。しかしここまでの `products` インデックスには、教科書だから許されていた大きな嘘があります。**データを人間が手で `bulk` 投入していた**ことです。

> 前提知識：フェーズ1（特に第5章の `products` インデックス）／フェーズ2
> この章にハンズオンはありません。**設計を理解する章**です。環境構築は次章から行います。

## 13.1 いま起きている問題 ― 「誰が正しいのか」

フェーズ1の第5章で、私たちは6件の商品をこう投入しました。

```http
POST /products/_bulk
{"index":{"_id":"1"}}
{"name":"軽量ノートパソコン 14インチ","category":"pc","price":98000,"in_stock":true}
...
```

これは学習用としては正しいやり方です。しかし本番のECサイトを想像してください。

- 商品担当者は**管理画面**から商品を登録・修正する
- 在庫は**受注システム**が売れるたびに減らす
- 価格は**バッチ**が深夜に一括更新する

これらはすべて **RDB（MySQL や PostgreSQL）に書き込まれます**。つまり、

> **データの正本はDBにあり、Elasticsearch はその「検索用のコピー」にすぎない。**

という関係になります。この関係を絵にすると、こうです。

```
        [管理画面] [受注システム] [バッチ]
             \         |          /
              \        |         /
               v       v        v
            +------------------------+
            |      MySQL (正本)      |   ← ここが真実
            |    products テーブル   |
            +------------------------+
                        |
                        |  ??? どうやって運ぶ ???
                        v
            +------------------------+
            |  Elasticsearch (複製)  |   ← 検索専用のコピー
            |  products インデックス |
            +------------------------+
```

この「???」の部分を設計するのがフェーズ3のテーマです。ここを雑に作ると、**検索結果に売り切れ商品が出続ける／値下げが反映されない／削除したはずの商品が出てくる**といった、ユーザーから見て最も信用を失う種類のバグが発生します。

> 📌 **用語**：DBのような書き込みの正本を **source of truth（信頼できる唯一の情報源）**、Elasticsearch のような読み取り専用の複製を **read model（読み取りモデル）** と呼びます。「書き込み用のモデル」と「読み取り用のモデル」を分ける設計は **CQRS**（Command Query Responsibility Segregation）と呼ばれ、検索エンジンの導入は事実上その一形態です。

## 13.2 いちばん素朴な方法と、その罠 ― 二重書き込み（dual write）

最初に誰もが思いつくのは、「アプリケーションがDBに書いたあと、続けて Elasticsearch にも書けばいい」という方法です。

```java
// 疑似コード（このコードは"やってはいけない例"です）
db.update("UPDATE products SET price = 89000 WHERE id = 1");
es.index("products", "1", newProductJson);
```

シンプルで、遅延もゼロ。一見すると完璧です。しかしこれは**分散システムにおける典型的なアンチパターン**であり、次の3つの形で必ず壊れます。

### 罠①：片方だけ成功する

```
時刻   アプリ                     MySQL           Elasticsearch
----------------------------------------------------------------
t1     DBを更新       ------->  price=89000
t2     ESに書き込み   --------------X (ネットワーク断)   price=98000 のまま
t3     例外発生。さて、DBをロールバックする？
       → もうCOMMIT済みなので戻せない
```

結果、**DBは89,000円、ESは98,000円**という不整合が永久に残ります。しかも誰も気づきません。気づくのはユーザーが「検索結果と商品ページで値段が違う」と問い合わせてきたときです。

逆順（ES先、DB後）にしても同じことで、今度は「DBに存在しない商品が検索でヒットする」という**幽霊ドキュメント**が生まれます。

> **なぜ解決できないのか**：DBのトランザクションは Elasticsearch を巻き込めません。「DBのコミットとESの書き込みを、両方成功か両方失敗にする」には分散トランザクション（2フェーズコミット）が必要ですが、Elasticsearch はそれをサポートしていませんし、仮にできても性能・運用コストが見合いません。

### 罠②：並行更新で順序が逆転する

2つのリクエストがほぼ同時に同じ商品を更新した場合を考えます。

```
リクエストA（価格を 89000 に）    リクエストB（価格を 79000 に）
--------------------------------------------------------------
t1  DB更新 → 89000
t2                                DB更新 → 79000
t3                                ES書き込み → 79000
t4  ES書き込み → 89000    ★ Aの方が遅れて到着した
--------------------------------------------------------------
最終状態： DB = 79000   /   ES = 89000  ← 食い違う
```

DBは行ロックで直列化してくれますが、**ESへの書き込みには何の順序保証もありません**。アプリのスレッドスケジューリングやネットワーク遅延次第で、古い値が後から上書きしてしまいます。

### 罠③：書き込み経路が増えるたびに実装漏れが起きる

冒頭の図のとおり、DBに書く主体は1つではありません。管理画面、受注システム、深夜バッチ、そして「本番DBに直接 `UPDATE` を打った運用担当者」。**このすべてにES書き込みコードを埋め込むことは、現実的に不可能です**。1つでも漏れれば、そこから静かにズレていきます。

> 💡 **コラム：二重書き込みを「マシ」にする Outbox パターン**
> どうしてもアプリ主導でイベントを出したい場合、**Outbox パターン**という定石があります。アプリはDBのトランザクション内で、業務テーブルの更新と一緒に `outbox` テーブルへ「変更しました」という1行を書きます。**同じトランザクションなので、両方成功か両方失敗しかありません**。あとは別プロセスが `outbox` テーブルを読んで Elasticsearch に反映します。
> 罠①は解決できますが、「outboxテーブルを誰がどう読むか」という問題が残ります。実はその答えがこの章のテーマである **CDC** で、Debezium には Outbox 専用の変換機能まで用意されています（フェーズ3の後半で触れます）。

## 13.3 同期方式の4つの選択肢

二重書き込み以外にどんな手があるのか、一覧で比較します。

| | ①二重書き込み | ②全件再構築 | ③ポーリング | ④CDC |
|---|---|---|---|---|
| やり方 | アプリがDBとESの両方に書く | 定期的に全件SELECTしてreindex | `updated_at > 前回時刻` を定期SELECT | DBのトランザクションログを読む |
| 反映の遅延 | ほぼゼロ | 数時間〜1日 | ポーリング間隔（数秒〜数分） | 1秒未満〜数秒 |
| DBへの負荷 | なし | 非常に大きい（全件走査） | 中（定期クエリ＋インデックス必要） | ほぼなし（ログを読むだけ） |
| 削除の検知 | できる | できる（作り直すので） | **できない**（行が消えるため） | **できる**（DELETEもログに載る） |
| 更新の取りこぼし | 実装漏れで起きる | 起きない | 起きうる（後述） | 起きない |
| 順序保証 | なし | ― | 弱い | あり（ログの順序＝コミット順） |
| アプリ改修 | 全書き込み箇所に必要 | 不要 | 不要（`updated_at` 列は必要） | **不要** |
| 実装・運用コスト | 低い（が壊れる） | 低い | 中 | **高い**（本章のテーマ） |

### ②全件再構築（full reindex）の位置づけ

「毎晩、DBから全件SELECTして新しいインデックスを作り直し、エイリアスを切り替える」という方式です。**単純で堅牢**という強みがあり、データ件数が少なく（数万件程度）、鮮度が1日単位で許されるなら**これが最良の選択**であることも多いです。実際、CDCを採用した現場でも「壊れたときに全件作り直せる仕組み」は必ず併設します。フェーズ3の後半で、この**再同期（リシンク）**の手順も扱います。

### ③ポーリングの弱点 ― 「一見動くが、静かに取りこぼす」

`updated_at` 列を使う方式は手軽で、多くの現場で最初に採用されます。しかし2つの厄介な落とし穴があります。

**落とし穴A：削除が検知できない**

```sql
DELETE FROM products WHERE id = 3;
```

行が消えてしまえば、次のSELECTには当然出てきません。「消えた」という事実自体をポーリングでは知りようがないのです。これを避けるには全商品を論理削除（`deleted_at` 列）に統一する必要がありますが、既存システムでそれを徹底するのは大工事です。

**落とし穴B：コミット順と `updated_at` の順が一致しない**

これが最も見つけにくいバグです。

```
時刻       トランザクションX                 ポーリング処理
------------------------------------------------------------------
10:00:00   BEGIN
10:00:01     UPDATE products SET
             updated_at = '10:00:01'        ← 値はこの時点で確定
10:00:02                                     ポーリング実行
                                             （> 09:59:00 の行を取得）
                                             ★ Xは未コミットなので見えない
                                             → 「前回時刻」を 10:00:02 に更新
10:00:05   COMMIT                            ← ここで初めて他から見える
10:01:00                                     ポーリング実行
                                             （> 10:00:02 の行を取得）
                                             ★ Xの行は updated_at=10:00:01
                                                なので条件に合わず、拾えない
------------------------------------------------------------------
結果：この更新は永久に Elasticsearch に届かない
```

長いトランザクションや、レプリカ遅延、サーバー間の時計ずれ（クロックスキュー）でも同じことが起きます。**「たまに1件だけ反映されない」という再現困難な障害**として現れるため、原因究明に何日も溶かすことになります。

> ⚠️ ポーリングを完全に否定するわけではありません。重複を許して安全側に倒す（前回時刻から少し巻き戻して重ねて取得する）など、緩和策はあります。ただし「削除」と「順序」の2点は本質的に解けません。

## 13.4 CDCとは何か ― トランザクションログを読む

**CDC（Change Data Capture／変更データキャプチャ）** とは、データベースで起きた行レベルの変更（INSERT / UPDATE / DELETE）を検知し、変更イベントの流れとして外部に取り出す技術です。

CDCには実装方式が3つあります。

| 方式 | 仕組み | 評価 |
|---|---|---|
| クエリベース | `updated_at` などを定期SELECT | 13.3の③そのもの。削除と順序に弱い |
| トリガーベース | DBトリガーで変更履歴テーブルに書く | 削除も拾えるが、**書き込み性能を犠牲にする**。トリガー管理も煩雑 |
| **ログベース** | **トランザクションログを読む** | 本命。アプリにもテーブルにも手を入れない |

Debezium が採用しているのは**ログベース**です。ここが理解の勘所なので、少し掘り下げます。

### なぜ「ログ」なのか

リレーショナルデータベースは、クラッシュしても復旧できるように、**すべての変更をコミット順に追記していくログファイル**を持っています。

| DB | ログの名前 | 備考 |
|---|---|---|
| **MySQL** | **binlog**（バイナリログ） | **本教科書で使用**。`ROW` 形式にすると変更前後の行の値が入る |
| PostgreSQL | WAL（Write-Ahead Log） | ロジカルデコーディング（`pgoutput`）で内容を読める |
| MariaDB | binlog | MySQL互換だが、Debezium 3.x では**専用コネクタ**が用意されている |
| SQL Server | トランザクションログ | CDC機能が標準で用意されている |
| Oracle | REDOログ | LogMiner 経由で読む |

このログは、そもそも**レプリケーション（レプリカへのデータ複製）に使われているもの**です。つまり、

> **CDCとは「Elasticsearch を、DBのレプリカの一種として扱う」技術である。**

と言い換えられます。Debezium は、DBから見れば「レプリカサーバーのフリをしてログを読みに来るクライアント」です。MySQL の場合、これは比喩ではなく**文字どおり**です。Debezium は自分に `server-id`（レプリカを識別する番号）を名乗らせ、レプリケーション用のプロトコルで binlog を受け取ります。`SHOW REPLICAS` を実行すると、Debezium が1台のレプリカとして表示されるほどです。だからこそ次の性質が手に入ります。

- **完全性**：コミットされた変更は必ずログに載る。取りこぼしがない
- **順序性**：ログはコミット順に並んでいる。逆転しない
- **削除も取れる**：`DELETE` もログに記録される
- **非侵襲**：アプリのコードにもテーブル定義にも手を入れない
- **低負荷**：本番テーブルへの追加クエリが発生しない

### 変更イベントはどんな形をしているか

Debezium が生成するイベントは、ざっくり次のような JSON です（実物はもっと冗長ですが、本質はこれだけです）。

```json
{
  "op": "u",                                  // c=作成 u=更新 d=削除 r=初期読み込み
  "ts_ms": 1785312000123,                     // Debeziumがイベントを処理した時刻
  "before": { "id": 1, "price": 98000, ... }, // 変更前の行
  "after":  { "id": 1, "price": 89000, ... }, // 変更後の行
  "source": {                                 // どこから来たか
    "connector": "mysql",
    "db": "shopdb", "table": "products",
    "server_id": 223344,                      // 変更を行ったMySQLサーバーのID
    "file": "binlog.000004",                  // binlogファイル名
    "pos": 1057,                              // そのファイル内の位置
    "row": 0,                                 //  ┗ 同一イベント内の何行目か
    "gtid": null,                             // GTIDを有効にすると入る
    "ts_ms": 1785312000100                    // DBで実際にコミットされた時刻
  }
}
```

注目してほしいのは **`before` と `after` の両方がある**ことと、**`source` にログ上の位置が入っている**ことです。

- `before`/`after` があるので「何がどう変わったか」が分かる
- **`file` + `pos` の組が binlog 上の座標**で、これがコミット順に増えていきます。つまり「どちらのイベントが新しいか」を機械的に判定できます。これは後の章で「古いイベントによる上書き」を防ぐ切り札になります（Elasticsearch の外部バージョニング機能と組み合わせます）

> ⚠️ **MySQL特有の注意**：PostgreSQL の `lsn` が単一の数値であるのに対し、MySQL の binlog 座標は **`file` と `pos` の2値の組**です。そのまま「バージョン番号」として使えないため、第17章では `source.ts_ms`（コミット時刻）を使う方法や、`file` と `pos` を1つの数値に合成する方法を検討します。ここが PostgreSQL 版との数少ない設計上の違いです。

## 13.5 なぜ間に Kafka を挟むのか

ここで素朴な疑問が出ます。「DBのログを読んで、そのまま Elasticsearch に書けばいいのでは？　なぜ Kafka という別のミドルウェアを増やすのか？」

もっともな疑問です。Kafka は運用対象が1つ増えるという、決して安くないコストを伴います。それでも挟む理由は5つあります。

```
【Kafkaなし】
     MySQL   --> [変換・投入プロセス] --> Elasticsearch
                          ↑
                  ここが落ちている間、
                  ES が止まるだけでなく、
                  変更をどこまで処理したかを
                  自力で管理する必要がある

【Kafkaあり】
     MySQL   --> Debezium --> [ Kafka topic ] --> Sink --> Elasticsearch
                                     |                （検索用）
                                     |
                                     +----> Sink --> データウェアハウス
                                     |
                                     +----> アプリ（キャッシュ削除・通知など）
                              ここに変更履歴が
                              数日分「溜まって」いる
```

**理由①：バッファになる**
Elasticsearch がメンテナンスで落ちても、Kafka にイベントが溜まり続けます。復旧後、続きから流し込めば追いつきます。
これは MySQL では特に重要です。**binlog は `binlog_expire_logs_seconds`（既定で30日）を過ぎると自動的に削除されます**。もし ES に直結していて、その停止が長引き、未読の binlog がパージされてしまったら、**「どこまで読んだか」の続きが永久に失われ、全件スナップショットからのやり直し**になります。Kafka を挟めば、Debezium は ES の状態と無関係に binlog を読み進められるため、この事故を構造的に防げます。

**理由②：リプレイできる**
「マッピングを変えたので、過去3日分を流し直したい」というとき、Kafka のオフセットを巻き戻すだけで再処理できます。DBに全件SELECTをかける必要がありません。**変更履歴が保存されていること自体が資産**です。

**理由③：出口を増やせる（fan-out）**
検索用ESだけでなく、分析用DWH、キャッシュ無効化、監査ログ、通知……と、同じ変更イベントを何人でも購読できます。しかも**購読者を増やしてもDBには一切影響しません**。これはCDC＋Kafkaの最大の価値です。

**理由④：疎結合になる**
DB側の担当とES側の担当が、Kafkaトピックという契約を挟んで独立して動けます。片方の障害がもう片方に直接伝播しません。

**理由⑤：順序が保たれる**
Kafka は「同じキー（＝同じ商品ID）のメッセージは同じパーティションに入り、その中では順序が保証される」という性質を持ちます。13.2の罠②（順序逆転）が、仕組みとして防がれます。

> 💡 **コラム：Kafka を使わない選択肢もある**
> Debezium には、Kafka を使わない **Debezium Server**（イベントを Kinesis / Pub/Sub / Redis などへ直接送る単体プロセス）と、**Debezium Embedded Engine**（自作アプリにライブラリとして組み込む）という形態もあります。「送り先が Elasticsearch 1つだけ」「小規模」なら、これらのほうが構成はずっと軽くなります。
> 本教科書で Kafka を挟むのは、**上の①〜⑤の恩恵を学ぶこと自体が目的**だからです。実務では「本当に Kafka が要るか」を毎回考えてください。要らないなら要らないと判断できることが、この章の理解のゴールでもあります。

## 13.6 フェーズ3で作るもの ― パイプラインの全体像

いよいよ設計図です。フェーズ3ではこれを段階的に組み上げます。

```
 ┌──────────────┐
 │    MySQL     │  shopdb.products テーブル（ここが正本）
 │              │  log_bin / binlog_format=ROW を有効化
 └──────┬───────┘
        │ ① レプリカとして binlog を購読
        v
 ┌───────────────────────────────────────────┐
 │            Kafka Connect（分散実行基盤）      │
 │  ┌─────────────────────┐                  │
 │  │   Debezium MySQL    │  ソースコネクタ      │
 │  │   Source Connector  │                   │
 │  └──────────┬──────────┘                  │
 └─────────────┼─────────────────────────────┘
               │ ② 変更イベント(JSON)を publish
               v
```

## 13.7 CDCを採用すると必ずぶつかる5つの論点

パイプラインは「つなげば終わり」ではありません。ここで**この先の章で何と戦うのか**を先に見せておきます。今すぐ理解できなくて構いません。「そういう問題があるらしい」と頭の隅に置いておくと、後の章の理解が一気に速くなります。

### 論点1：at-least-once と冪等性

Kafka の標準的な配信保証は **at-least-once（少なくとも1回）** です。つまり、**同じイベントが2回届くことがあります**（コネクタが再起動したときなど）。

これは Elasticsearch との相性が良い部分です。ESは `_id` を指定して書き込めば「同じIDなら上書き（upsert）」になるため、**同じイベントを何度適用しても結果が同じ**（＝**冪等**）になります。逆に言えば、**`_id` にDBの主キーを使うことが必須**です。ESに自動採番させると、再送のたびに重複ドキュメントが生まれます。

### 論点2：削除をどう伝えるか

Debezium は削除時に2つのメッセージを出します。

1. `op: "d"` のイベント（`before` に消える前の値が入る）
2. **tombstone（墓石）** ＝ **キーだけあって値が `null`** のメッセージ

シンクコネクタ側で「値がnullのメッセージが来たらESからDELETEする」と設定して初めて、削除が反映されます。**デフォルト設定では削除が無視される**こともあり、ここは第16章の重要ポイントです。

### 論点3：順序と「古い値による上書き」

Kafka はパーティション内の順序を守りますが、シンク側が並列化されていたり、リトライが挟まったりすると、まれに古いイベントが後から適用されかねません。これを防ぐのが Elasticsearch の **外部バージョニング**（`version_type=external`）で、**単調増加する値をバージョン番号として渡す**ことで「今より古い版は拒否する」動きにできます。13.2の罠②への構造的な回答です。MySQL では 13.4 で触れたとおり binlog 座標が `file` + `pos` の2値なので、何をバージョン番号にするかがそのまま設計課題になります。

### 論点4：スキーマ変更（ALTER TABLE）

DBに列が増えたとき、Elasticsearch のマッピングはどうなるでしょうか。ESは**一度決めたフィールドの型を後から変更できません**（第3章）。CDCパイプラインでは「上流のスキーマ変更が下流を壊す」事故が定番です。動的マッピングに任せるのか、明示マッピングで固定して未知フィールドを無視するのか。第17章で扱います。

### 論点5：非正規化 ― これが本当の難所

DBは正規化されています。しかし Elasticsearch は**1ドキュメントに検索したい情報が全部入っている**ことを前提とした設計を好みます（第3章）。

```
【DB（正規化）】                     【ES（非正規化）】
 products                            products インデックス
  id, name, price, category_id        {
 categories                             "name": "軽量ノートPC",
  id, name                              "price": 98000,
 product_tags                           "category_name": "パソコン", ← categoriesから
  product_id, tag_id                    "tags": ["軽量","14インチ"]  ← tagsから
 tags                                 }
  id, name
```

CDCは**テーブル単位でイベントを出します**。`categories` テーブルのカテゴリ名が変わったとき、そのカテゴリに属する何千件もの商品ドキュメントを更新しなければなりません。この「**ストリーム上でJOINする**」問題こそが、CDC × 検索インデックスの本丸です。第18章で正面から扱います。

## まとめ

- Elasticsearch は検索用の**複製**であり、正本はDBにある。両者をどう同期するかは避けて通れない設計課題である
- **二重書き込み（dual write）** は、①片方だけ成功する ②並行更新で順序が逆転する ③書き込み経路の実装漏れ、の3つで必ず壊れる。分散トランザクションでは救えない
- 同期方式には「全件再構築」「ポーリング」「CDC」がある。全件再構築は小規模なら十分有効。ポーリングは**削除を検知できず、コミット順と `updated_at` 順のズレで静かに取りこぼす**
- **CDC（ログベース）** は、DBのトランザクションログ（MySQLのbinlog、PostgreSQLのWAL）を読む方式。レプリケーションの仕組みに相乗りするため、完全・順序保証あり・削除も取得可能・非侵襲・低負荷という性質を持つ。Debezium は MySQL に対して**1台のレプリカとして振る舞う**
- 間に **Kafka** を挟む理由は、①バッファ ②リプレイ ③fan-out ④疎結合 ⑤順序保証 の5つ。逆に送り先が1つで小規模なら Debezium Server などの軽い構成も選択肢になる
- フェーズ3では **MySQL（binlog／ROW形式）→ Debezium → Kafka → ESシンクコネクタ → Elasticsearch** を構築する
- CDCの実務的な論点は、**冪等性（`_id` に主キーを使う）／削除とtombstone／古い値の上書き防止／スキーマ変更／非正規化とJOIN** の5つ

## 理解度チェック

**問1.** 「アプリケーションがDBを更新した直後に、同じ処理の中で Elasticsearch にも書き込む」方式の問題点を、**3つ**挙げてください。

**問2.** `updated_at` 列を使ったポーリング方式では、削除された商品が Elasticsearch に残り続けます。なぜですか。また、それでもポーリング方式で削除に対応したい場合、どんな前提が必要になりますか。

**問3.** CDCが「トランザクションログ（MySQLならbinlog）を読む」方式を採るのはなぜですか。トリガーを使う方式と比べた利点を2つ挙げてください。

**問4.** DBとElasticsearchの間に Kafka を挟むメリットを3つ挙げてください。また、Kafka を挟まないほうがよいのはどんなケースですか。

**問5.** Kafka の配信保証は at-least-once（同じイベントが2回届きうる）です。それでも Elasticsearch 側でデータが壊れないようにするには、ドキュメントの `_id` をどう決めるべきですか。理由も述べてください。

<details>
<summary>解答を見る</summary>

**問1.**
1. **片方だけ成功する**：DBコミット後にES書き込みが失敗しても、DBはもうロールバックできず、不整合が永久に残る（逆順ならDBに存在しない幽霊ドキュメントが残る）。
2. **並行更新で順序が逆転する**：DBは行ロックで直列化されるが、ESへの書き込み順序は保証されないため、古い値が新しい値を上書きしうる。
3. **書き込み経路すべてに実装が必要**：管理画面・バッチ・他システム・手動SQLなど、DBに書くすべての箇所にES書き込みを埋め込むのは非現実的で、1つ漏れれば静かにズレる。

**問2.**
削除されると**行そのものがテーブルから消える**ため、`SELECT ... WHERE updated_at > ?` の結果に一切現れず、「消えた」という事実を検知する手段がないから。
対応するには、物理削除をやめて `deleted_at` 列などによる**論理削除に統一する**という前提が必要（かつ、すべての削除経路でそれが守られている必要がある）。

**問3.**
トランザクションログはDB自身が**クラッシュリカバリとレプリケーションのために必ず書いている**ものなので、そこに相乗りすればコミットされた変更を漏れなく・コミット順で取得できるから。
トリガー方式と比べた利点（2つ）：
- **書き込み性能を落とさない**（トリガーは各INSERT/UPDATE/DELETEに同期的な追加処理を挟むため、本番トランザクションが重くなる）
- **アプリにもスキーマにも手を入れなくてよい**（トリガーは全対象テーブルへの作成・保守が必要で、DDL変更のたびに管理が発生する）
（他に「削除も含めて確実に取得できる」「取得順序がコミット順と一致する」なども可）

**問4.**
メリット（以下から3つ）
- **バッファ**：ES側が停止していてもイベントが溜まり、復旧後に追いつける。ES停止が長引いて未読のbinlogがパージされ、全件やり直しになる事故も防げる
- **リプレイ**：オフセットを巻き戻すだけで過去のイベントを再処理でき、マッピング変更後の作り直しが容易
- **fan-out**：同じイベントをDWH・キャッシュ・通知など複数の購読者に配れ、購読者を増やしてもDBに負荷がかからない
- **疎結合／障害の局所化**
- **キー単位の順序保証**

Kafkaを挟まないほうがよいケース：送り先が Elasticsearch 1つだけで、再利用や複数購読の予定がなく、規模も小さい場合。運用対象を増やすコストが恩恵を上回るため、Debezium Server や Embedded Engine のほうが適する。

**問5.**
**DBの主キー（例：`products.id`）をそのまま `_id` に使う。**
Elasticsearch は `_id` を指定した書き込みを「同じIDなら上書き」として扱うため、同じイベントが何回届いても最終結果が変わらない（**冪等**になる）。逆にESの自動採番に任せると、再送のたびに同じ商品のドキュメントが増殖し、検索結果に重複が出てしまう。

</details>
