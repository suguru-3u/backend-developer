# 第12章　ベクトル検索・セマンティック検索 ― dense_vector / knn / semantic_text

> **フェーズ2 最終章**
> 第7章の BM25 から本章まで、検索の土台はずっと「**語（トークン）の一致**」でした。シノニムや正規化で揺れを吸収しても、根っこは「同じ語が出てくるか」です。ところが「音楽を聴く道具」で検索して**イヤホンやスピーカー**を出したい――語がひとつも一致しなくても**意味で**当てたい。これはまったく別の仕組み、ベクトル検索が必要です。フェーズ2の集大成として、意味の検索と、キーワード検索との合わせ技（ハイブリッド）まで見ていきます。

---

## 学習目標

この章を終えると、次のことができるようになります。

- キーワード検索（字面）と意味検索（ベクトル）の違いを説明できる
- 埋め込み（embedding）ベクトルと「近さ＝意味の近さ」の考え方を理解する
- `dense_vector` フィールドを定義し、**自前のベクトル**を投入して `knn` 検索できる
- kNN の主要パラメータ（`k` / `num_candidates` / `similarity`）と近似探索（HNSW）の性質を説明できる
- `semantic_text` と `semantic` クエリで、推論を内蔵した意味検索の構成を理解する（前提と制約も）
- 疎ベクトル（ELSER）と密ベクトルの違い、日本語での注意点を説明できる
- **ハイブリッド検索**（BM25 ＋ ベクトル）の考え方を理解する

## この章の前提と進め方

第8〜11章と同じ `products`（6件）を題材にします。ただし本章は**動作前提が2段階**に分かれます。

- **12.3〜12.5（自前ベクトル＋knn）**：学習用の single-node・無償構成でも動きます。ベクトル検索（`dense_vector` / `knn`）自体は追加のMLや外部モデルなしで使えるためです。まずここを手で動かします。
- **12.6（semantic_text）**：埋め込みを内蔵生成する推奨アプローチですが、**推論エンドポイント（Inference API）・MLの実行環境・ライセンス**の前提があります。最小構成では追加設定が要る場合があるため、「概念を理解し、環境が整えば試す」位置づけで扱います（自分の環境の要件は必ず確認してください）。

> 本章のベクトルは概念理解のため **3次元の作り物**を使います。実際の埋め込みは 384 次元や 768 次元などが一般的です。

## 12.1　なぜキーワード検索では足りないのか

BM25 は「クエリの語」と「文書の語」が一致してこそスコアが付きます。シノニムで補えるのは、あらかじめ辞書に書いた関係だけです。

```
クエリ:  「音楽を聴く道具」
文書1:   「ワイヤレスイヤホン。高音質…」
             → 「音楽」「聴く」「道具」の語は文書に無い
             → BM25 では当たらない（取りこぼし）
```

人間には「イヤホンは音楽を聴く道具」だと分かりますが、字面の一致しか見ない検索には分かりません。この**意味の一致**を扱うのがベクトル検索です。

---

## 12.2　埋め込みベクトルという発想

**埋め込み（embedding）** とは、テキストを機械学習モデルで「数百次元の数値の並び（ベクトル）」に変換したものです。うまく訓練されたモデルでは、**意味が近いテキストほどベクトルが近い場所に配置**されます。

```
        意味空間（イメージ・2次元に簡略化）
          ▲
          │      ●イヤホン
          │    ●スピーカー
          │              ●音楽を聴く道具   ← クエリもベクトル化
          │
          │                      ●ノートパソコン
          └──────────────────────────────▶
```

検索は「クエリのベクトルに**近い**文書ベクトルを探す」問題になります。この「近いものを k 個探す」処理が **kNN（k-Nearest Neighbor：k近傍）** です。近さは距離や角度で測ります。

---

## 12.3　dense_vector フィールドを定義する

密ベクトル（すべての次元に値が入るベクトル）は `dense_vector` 型で持ちます。

```json
PUT /products_vec
{
  "mappings": {
    "properties": {
      "name":       { "type": "text", "analyzer": "kuromoji" },
      "category":   { "type": "keyword" },
      "embedding":  {
        "type": "dense_vector",
        "dims": 3,
        "index": true,
        "similarity": "cosine"
      }
    }
  }
}
```

- `dims`：ベクトルの次元数。**投入するベクトルと一致**している必要があります。
- `index: true`（既定）：kNN 用のインデックス（HNSW グラフ）を作ります。
- `similarity`：近さの測り方。`cosine`（コサイン類似度）／`dot_product`（内積）／`l2_norm`（ユークリッド距離）／`max_inner_product` から選びます。テキスト埋め込みでは `cosine` がよく使われます。

> **9.x での既定と挙動**
> - 浮動小数ベクトルは既定で**自動量子化**されてインデックスされます（次元が大きい場合は BBQ、そうでなければ int8 系の HNSW など）。量子化はメモリと速度を大きく改善し、精度低下はわずかです。学習では既定のままで構いません。
> - `dense_vector` フィールドは既定で **`_source` に含まれず**、検索レスポンスに生ベクトルが返りません（レスポンス肥大の防止）。値を確認したいときは明示的に取得設定が必要です。
> - `dense_vector` は**集計やソートの対象にできません**（第11章の集計対象外）。

## 12.4　ベクトルを投入して knn 検索する

3次元の作り物ベクトルで、いくつか商品を入れてみます（値は「オーディオ系は近い場所、パソコンは遠い場所」を意図した手作りです）。

```json
POST /products_vec/_bulk
{ "index": { "_id": "1" } }
{ "name": "ワイヤレスイヤホン", "category": "オーディオ", "embedding": [0.9, 0.1, 0.0] }
{ "index": { "_id": "5" } }
{ "name": "Bluetoothスピーカー", "category": "オーディオ", "embedding": [0.8, 0.2, 0.0] }
{ "index": { "_id": "2" } }
{ "name": "ノートパソコン", "category": "パソコン", "embedding": [0.0, 0.1, 0.9] }
```

「音楽を聴く道具」に相当するクエリベクトル（本来はモデルが生成）を `[0.85, 0.15, 0.0]` と仮定して、近い順に探します。

```json
GET /products_vec/_search
{
  "knn": {
    "field": "embedding",
    "query_vector": [0.85, 0.15, 0.0],
    "k": 2,
    "num_candidates": 10
  }
}
```

イヤホン・スピーカーが上位に、ノートパソコンは下位（または圏外）になります。**語がひとつも一致していなくても、ベクトルの近さで意味的に関連する商品**を引けました。

### k と num_candidates

- `k`：最終的に返す近傍の数。
- `num_candidates`：各シャードで HNSW を辿るときに検討する候補数。**`k` より十分大きく**します（目安は数十〜数百）。

kNN の探索（HNSW）は速度のために**近似**アルゴリズムを使います。`num_candidates` を増やすほど精度（recall）が上がり、代わりに遅くなります。逆に `num_candidates` を `k` と同じくらいまで下げると、探索が退化して取りこぼしが急増します。**「速度 ↔ 精度」のツマミが num_candidates**だと覚えてください。

### knn オプションと knn クエリ

kNN には2つの書き方があります。

- **`knn` 検索オプション**（上の例）：`_search` 直下に書くトップレベル指定。シンプルな近傍検索向き。
- **`knn` クエリ**：クエリ DSL の中に書ける形。`bool` の中に入れて他のクエリと組み合わせられる（ハイブリッド検索で使う。12.7）。

### フィルタつき kNN

「在庫ありの中から意味が近いもの」のように、条件で絞りつつ近傍探索できます。**フィルタは knn の中に書く**のがコツです。こうすると HNSW の探索そのものにフィルタが押し込まれ、絞り込んでも取りこぼしにくくなります（外側の `bool.filter` で包むより recall が保たれる）。

```json
GET /products_vec/_search
{
  "knn": {
    "field": "embedding",
    "query_vector": [0.85, 0.15, 0.0],
    "k": 2,
    "num_candidates": 10,
    "filter": { "term": { "category": "オーディオ" } }
  }
}
```

## 12.5　ベクトルはどこから来るのか

12.4 では手でベクトルを書きましたが、実務では**埋め込みモデル**が生成します。方法は大きく2つです。

1. **自前生成（Bring Your Own Vectors）**：外部（Python など）でモデルを動かしてベクトル化し、その配列を Elasticsearch に投入する。学習・小規模ならこれが手軽で、追加のML環境も要りません。
2. **Elasticsearch 内で生成**：推論エンドポイントを設定し、取り込み時に自動でベクトル化する（次節の `semantic_text` がこの発展形）。

> **日本語での注意**：埋め込みモデルには対応言語があります。後述の ELSER は主に**英語**向けです。日本語の商品を意味検索するなら、**多言語対応の埋め込みモデル**（multilingual-e5 系など）を選ぶ必要があります。モデル選びが検索品質を大きく左右します。

## 12.6　semantic_text ― 推論を内蔵する（推奨アプローチ）

自前でベクトル化・チャンク分割・マッピング設計を行うのは手間です。**`semantic_text`** はこれらを**自動化**するフィールド型で、9.x の意味検索では第一候補とされています。

```json
PUT /products_semantic
{
  "mappings": {
    "properties": {
      "description": {
        "type": "semantic_text",
        "inference_id": ".elser-2-elasticsearch"
      }
    }
  }
}
```

`semantic_text` は次を自動でやってくれます。

- 推論エンドポイント（`inference_id`）に応じて、`sparse_vector` か `dense_vector` か、次元数や類似度などの**マッピングを自動選択**。
- **取り込み時に自動で埋め込み生成**（別途インジェストパイプラインを組む必要がない）。
- 長い文章の**チャンク分割**も自動。

テキストをそのまま入れて、`semantic` クエリで自然文検索します。

```json
GET /products_semantic/_search
{
  "query": {
    "semantic": {
      "field": "description",
      "query": "音楽を聴く道具"
    }
  }
}
```

クエリ文も同じ推論エンドポイントでベクトル化され、意味の近い文書が返ります。

> **前提と制約（重要）**
> - `semantic_text` は**推論エンドポイント**を使うため、取り込み・検索時に **Inference API** を呼びます。これには適切な**ライセンス**や、モデルを動かす**MLの実行環境**（ELSER なら相応のメモリを持つMLノード）が必要です。
> - `inference_id` を省略したときの**既定エンドポイントはバージョンや実行環境で変わります**（例：Elastic Stack 9.0〜9.2 の自ホスト環境では ELSER 系が既定、Cloud の新しめのバージョンでは別の多言語モデルが既定、など）。既定に頼ると、環境間で埋め込みモデルが食い違い、**同一エイリアス配下で検索結果が乱れる**ことがあります。実務では `inference_id` を明示するのが安全です。
> - 学習用の最小 single-node 構成では、これらの前提が揃わず動かないことがあります。その場合は 12.3〜12.5 の**自前ベクトル＋knn** で意味検索の感覚をつかみ、`semantic_text` は環境を整えてから試すのがよいでしょう。

### 疎ベクトル（ELSER）と密ベクトル

- **密ベクトル（dense）**：全次元に値が入るベクトル。汎用の埋め込みモデルが出力。多言語モデルを選べば日本語も扱える。
- **疎ベクトル（sparse）**：ほとんどの次元が 0 で、意味のある少数の「語の重み」だけを持つ。Elastic の **ELSER**（Elastic Learned Sparse EncodeR）が代表で、`sparse_vector` 型に格納する。キーワード検索に近い解釈しやすさが利点だが、**主に英語向け**。

`semantic_text` は、指定した推論エンドポイントに応じて、この密／疎を**自動で使い分けて**くれます。

## 12.7　ハイブリッド検索 ― 字面 × 意味

意味検索は強力ですが万能ではありません。型番・商品コード・固有名詞のような**厳密な字面一致**は、むしろ BM25 が得意です。そこで両方を組み合わせる**ハイブリッド検索**が実務の定番になります。

```
   BM25（字面）        ベクトル（意味）
        │                  │
        └────── 合成 ───────┘
                 │
        両方の良さを取る
```

もっとも素朴な合成は、`bool` の `should` に字面クエリと `knn` クエリを並べて**スコアを足す**方法です。

```json
GET /products_vec/_search
{
  "query": {
    "bool": {
      "should": [
        { "match": { "name": "スピーカー" } },
        { "knn": {
            "field": "embedding",
            "query_vector": [0.85, 0.15, 0.0],
            "num_candidates": 10
        } }
      ]
    }
  }
}
```

ただし BM25 と kNN では**スコアの尺度が違う**ため、単純な足し算ではバランスが崩れがちです。これを解決するのが **RRF（Reciprocal Rank Fusion：順位に基づく融合）** で、9.x では **retriever（リトリーバー）API** を使って字面検索と意味検索の**順位**を公平に統合できます。まずは「字面と意味を両取りする発想」を押さえ、融合の実装は retriever を使う、と覚えておけば十分です。

---

## まとめ

- キーワード検索は字面の一致が前提。**意味は近いが語が違う**取りこぼしを埋めるのがベクトル検索。
- **埋め込み**はテキストをベクトル化したもので、意味が近いほどベクトルが近い。近傍探索が **kNN**。
- `dense_vector`（`dims` / `index` / `similarity`）にベクトルを持たせ、`knn` で探索する。自前ベクトル＋knn は最小構成でも動く。
- kNN は近似（HNSW）。**`num_candidates` が速度↔精度のツマミ**。フィルタは knn の中に書くと recall が保たれる。9.x は既定で自動量子化し、`dense_vector` は既定で `_source` に含まれず、集計/ソート不可。
- `semantic_text` ＋ `semantic` クエリは、埋め込み生成・チャンク分割・マッピングを自動化する推奨アプローチ。ただし**推論エンドポイント・ML環境・ライセンス**の前提がある。`inference_id` は明示が安全。
- 日本語では**多言語埋め込みモデル**を選ぶ（ELSER は主に英語・疎ベクトル）。
- 実務は**ハイブリッド検索**（BM25×ベクトル）が定番。尺度差の融合には **RRF（retriever API）**。

## 理解度チェック

**Q1.** 「音楽を聴く道具」で検索してイヤホンを出したい。BM25 だけでは難しいのはなぜですか。

<details><summary>解答</summary>

BM25 は**クエリの語と文書の語の一致**でスコアを付けます。「音楽」「聴く」「道具」がイヤホンの文書に無ければ当たりません。意味は近くても字面が違うため取りこぼします。これを埋めるのがベクトル（意味）検索です。
</details>

**Q2.** kNN の `num_candidates` を `k` と同じくらいまで小さくすると何が起きますか。

<details><summary>解答</summary>

HNSW の近似探索が退化し、取りこぼし（recall の低下）が急増します。`num_candidates` は `k` より十分大きく取り、精度が要るほど大きくします（速度とのトレードオフ）。
</details>

**Q3.** 「在庫ありの中から意味が近いもの」を探すとき、フィルタは knn の内側と外側どちらに書くべきですか。理由も。

<details><summary>解答</summary>

**knn の内側**（`knn` の `filter`）に書きます。フィルタが HNSW の探索そのものに押し込まれ、絞り込んでも取りこぼしにくくなります。外側の `bool.filter` で包むと、選択的なフィルタで recall が落ちやすくなります。
</details>

**Q4.** `semantic_text` を使うと、自前でベクトル検索を組む場合に比べて何が自動化されますか。

<details><summary>解答</summary>

推論エンドポイントに応じた**マッピングの自動選択**（密/疎・次元・類似度）、**取り込み時の埋め込み自動生成**（インジェストパイプライン不要）、長文の**チャンク分割**が自動化されます。代わりに推論エンドポイント・ML環境・ライセンスの前提が必要です。
</details>

**Q5.** 日本語の商品を意味検索するとき、モデル選びで注意すべき点は。

<details><summary>解答</summary>

ELSER は主に**英語**向け（疎ベクトル）なので、日本語では**多言語対応の密ベクトルモデル**（multilingual-e5 系など）を選ぶ必要があります。モデルの対応言語が検索品質を大きく左右します。
</details>

## フェーズ2の総括と次の一歩

フェーズ2「検索の改善」を走り切りました。第8章の重み付けで関連度を意図どおりに曲げ、第9章のシノニムと第10章の正規化で入力の揺れを吸収し、第11章の集計でファセットやダッシュボードを組み、そして第12章で字面を超えた意味検索とハイブリッドまで到達しました。**「ゆるく拾い、賢く並べ、俯瞰し、意味で当てる」**――現代的な検索体験の主要ピースが揃ったことになります。

ここから先（フェーズ3以降）は、いよいよ **Kafka / Debezium** と組み合わせ、データベースの変更を Elasticsearch にリアルタイムで流し込む **CDC（Change Data Capture）パイプライン**へ進みます。これまで手で `_bulk` していたデータ投入が、「ソースDBを更新したら自動で検索インデックスも最新になる」仕組みに変わります。検索の作り込み（フェーズ2）と、データを絶やさず届ける配管（フェーズ3）が合流する地点です。
