# 第9章　シノニム（類義語）辞書 ― synonym_graph と Synonyms API

> **前章のふりかえり**
> 第8章では、BM25 が出したスコアを boost・multi_match・function_score で「意図どおりに曲げる」方法を学びました。しかし重み付けは、**そもそも語がヒットしていること**が前提です。ユーザーが「イヤフォン」と打ったのに、商品名が「イヤホン」だと1件も当たりません。この**取りこぼし（recall の穴）**を埋めるのがシノニム（類義語）です。

---

## 学習目標

この章を終えると、次のことができるようになります。

- シノニムが「検索の取りこぼし」を減らす仕組みを説明できる
- 2種類のルール形式（**equivalent＝双方向** と **explicit（`=>`）＝一方向**）を使い分けられる
- `synonym` と `synonym_graph` の違いを理解し、**複数語シノニムには synonym_graph を検索時に使う**理由を説明できる
- **インデックス時展開**と**検索時展開**のトレードオフを説明し、適切に選べる
- 既存の `products` インデックスに、検索時シノニムを後付けできる（close → settings → open → search_analyzer 更新）
- **Synonyms API** で辞書をAPI管理し、`updateable: true` によって再インデックスなしで更新できる

---

## この章のサンプルデータ（前提）

第8章と同じ `products`（6件）を使います。関係するのは主に次の商品です。

| id | name | 説明文に含まれる語（例） |
|---|---|---|
| 1 | ワイヤレスイヤホン | イヤホン、ノイズキャンセリング |
| 2 | ノートパソコン | パソコン、軽量、ビジネス |
| 5 | Bluetoothスピーカー | スピーカー、防水、ポータブル |

シノニムは `text` フィールド（`name` / `description`）に効きます。`keyword` フィールド（`category` / `tags`）はアナライザーを通らないため、シノニムの対象外である点に注意してください。

## 9.1　なぜシノニムが必要か

検索は「ユーザーが打った語」と「インデックスに入っている語」が**同じトークンにならないと一致しない**のが原則です（第4章のアナライザーの話）。ところが自然言語では、同じものを違う言い方で表します。

- 表記ゆらぎ：イヤホン ／ イヤフォン
- 略語・別名：PC ／ パソコン、NC ／ ノイズキャンセリング
- 英語・カナ：speaker ／ スピーカー、Bluetooth ／ ブルートゥース

シノニムは「これらは同じ意味」という辞書を用意し、**検索の途中でトークンを増やして**取りこぼしを防ぎます。

```
ユーザー入力： 「イヤフォン」
                    │
                    ▼  シノニム展開（イヤホン, イヤフォン は同義）
        ┌───────────────────────────┐
        │ 検索トークン: イヤフォン / イヤホン │
        └───────────────────────────┘
                    │
                    ▼
   商品1「ワイヤレスイヤホン」に  ← 「イヤホン」でヒット！
```

> **注意：シノニムは諸刃の剣**
> 展開しすぎると、無関係な文書まで拾って**precision（適合率）が下がる**ことがあります。「拾える件数（recall）」と「関連度（precision）」はしばしばトレードオフです。辞書を足したら、必ずいくつかのクエリで結果を見比べてから本番投入しましょう。

## 9.2　ルールの2形式 ― equivalent と explicit

シノニムのルールには2つの書き方があります。**この違いはランキングにも影響する**ので、最初に押さえます。

### equivalent（双方向・カンマ区切り）

カンマで並べた語を**すべて相互に同義**とします。

```
イヤホン, イヤフォン
ノートパソコン, ノートPC, ラップトップ
```

「イヤホン」で検索しても「イヤフォン」で検索しても、互いにヒットします。

### explicit（一方向・`=>`）

`=>` の**左辺を右辺に展開**します。方向は一方通行です。

```
PC => パソコン
sf => san francisco
```

「PC」で検索すると「パソコン」にも展開されてヒットしますが、逆に「パソコン」で検索しても「PC」には展開されません。「入力の揺れは吸収したいが、正規語の方は広げたくない」ときに使います。

> **コラム：equivalent と explicit を混同するとランキングが壊れる**
> 双方向のつもりで一方向ルールを書く（またはその逆）と、「片方の語でしか当たらない」「意図しない語まで展開される」といった不具合が静かに混ざります。**辞書を書くときは、各行がどちらの形式かを意識する**のが鉄則です。

## 9.3　トークンフィルタで展開する ― synonym と synonym_graph

シノニムは**トークンフィルタ**として、アナライザーの解析チェーンに組み込みます（第4章の続き）。フィルタは2種類あります。

| フィルタ | 特徴 | 複数語シノニム | 使う場所 |
|---|---|---|---|
| `synonym` | 平坦なトークン列を置換・展開。単語シノニムは正しい | **位置がずれてフレーズ検索が壊れることがある** | インデックス時・検索時どちらも可 |
| `synonym_graph` | トークン**グラフ**を生成し、複数語も正しく扱う | **正しく扱える** | **検索アナライザー専用** |

### なぜ synonym_graph は「検索時専用」なのか

複数語シノニム（例：`ノートパソコン, ラップトップ`）を正しく扱うには、「1語 ↔ 複数語」を並行して表す**トークングラフ**が必要です。ところが **Lucene のインデックスはトークングラフをそのまま保存できません**（インデックス時はグラフを平坦化＝flatten せざるを得ず、複数語の位置情報が崩れる）。

そのため、複数語を正しく扱いたいなら **synonym_graph を検索アナライザー側で使う**のが唯一の正解になります。検索時のクエリ解析はグラフのまま `match` / `query_string` / `simple_query_string` に渡され、正しく展開されます。

```
インデックス時に複数語シノニムを入れると…
  ノートパソコン ─(flatten)→ 位置がつぶれる → フレーズ検索が壊れる  ✗

検索時に synonym_graph を使うと…
  クエリ「ラップトップ」→ グラフ展開 → ノート+パソコン として正しく照合  ✓
```

このため本章では、**検索時展開＋synonym_graph** を基本形として進めます。

## 9.4　インデックス時展開 vs 検索時展開

シノニムを「いつ」展開するかで、性質が大きく変わります。

| 観点 | インデックス時展開 | 検索時展開（推奨） |
|---|---|---|
| 展開のタイミング | ドキュメント登録時にトークンを増やして保存 | 検索クエリを解析するときに展開 |
| インデックスサイズ | 大きくなる | 変わらない |
| 検索速度 | 速い（展開済み） | やや遅い（検索のたびに展開） |
| 辞書の更新 | **再インデックスが必要** | **再インデックス不要**（リロードで反映） |
| 複数語シノニム | 壊れやすい（`synonym_graph` 不可） | 正しい（`synonym_graph` 可） |
| スコアへの影響 | 展開語も語彙統計に混ざる | 元の統計を保ちやすい |

**結論：迷ったら検索時展開。** 更新の柔軟さと複数語対応が効くためです。インデックス時展開は「文法変化形の吸収（stemmer 代わり）」のように、**めったに変わらない安定した言語規則**に限って使うのが目安です。

> **`updateable: true` の制約**
> 検索時に更新可能なシノニムを使うには、フィルタに `updateable: true` を付けます。ただしこの設定を付けたフィルタを含むアナライザーは、**検索アナライザーとしてしか使えなくなります**（インデックス時には使えない）。また `updateable` は**インライン `synonyms` では使えず**、ファイル（`synonyms_path`）か **Synonyms API（`synonyms_set`）** と組み合わせる必要があります。

## 9.5　まず `_analyze` で展開を「見る」

インデックスをいじる前に、`_analyze` API でシノニム展開の挙動を確認しましょう。フィルタをその場で定義でき、インデックスへの影響もありません。

```json
POST /_analyze
{
  "tokenizer": "kuromoji_tokenizer",
  "filter": [
    "kuromoji_baseform",
    "lowercase",
    {
      "type": "synonym_graph",
      "synonyms": [
        "イヤホン, イヤフォン",
        "PC => パソコン"
      ]
    }
  ],
  "text": "イヤフォン"
}
```

**期待される出力**：`イヤフォン` と `イヤホン` の**両方**のトークンが返ります（equivalent なので双方向に展開）。`text` を `"PC"` にすると `パソコン` が返り（explicit で一方向）、逆に `"パソコン"` では `PC` は出てきません。

> **順序の注意**：`lowercase` は `synonym_graph` より**前**に置きます。先に小文字化しておかないと、「PC」と「pc」が別トークン扱いになり、辞書に一致しなくなります。一般に、正規化系のフィルタはシノニムより前に置きます。

## 9.6　`products` に検索時シノニムを後付けする

既存インデックスにも、検索時シノニムなら**再インデックスせずに**適用できます（`search_analyzer` は既存フィールドでも更新できるため）。ただし、新しいフィルタ／アナライザーを**index settings に追加するにはインデックスを一度 close する**必要があります。手順は次の4ステップです。

### ステップ0：先に Synonyms API で辞書を作る（後述の9.7で詳説）

アナライザーが参照する辞書は、**先に存在している必要があります**。

```json
PUT /_synonyms/products-synonyms
{
  "synonyms_set": [
    { "id": "earphone", "synonyms": "イヤホン, イヤフォン" },
    { "id": "headphone", "synonyms": "ヘッドホン, ヘッドフォン" },
    { "id": "pc",        "synonyms": "PC => パソコン" }
  ]
}
```

### ステップ1：インデックスを閉じる

```json
POST /products/_close
```

### ステップ2：フィルタと検索アナライザーを追加

```json
PUT /products/_settings
{
  "analysis": {
    "filter": {
      "products_synonym_filter": {
        "type": "synonym_graph",
        "synonyms_set": "products-synonyms",
        "updateable": true
      }
    },
    "analyzer": {
      "kuromoji_search_synonym": {
        "type": "custom",
        "tokenizer": "kuromoji_tokenizer",
        "filter": [
          "kuromoji_baseform",
          "lowercase",
          "products_synonym_filter"
        ]
      }
    }
  }
}
```

### ステップ3：インデックスを開く

```json
POST /products/_open
```

### ステップ4：`name` / `description` の search_analyzer を差し替える

```json
PUT /products/_mapping
{
  "properties": {
    "name":        { "type": "text", "analyzer": "kuromoji", "search_analyzer": "kuromoji_search_synonym" },
    "description": { "type": "text", "analyzer": "kuromoji", "search_analyzer": "kuromoji_search_synonym" }
  }
}
```

> `analyzer`（インデックス時）は**変更できません**。ここでは第4章で設定した値（この例では `kuromoji`）をそのまま指定し、`search_analyzer` だけを新しいものに差し替えています。実際に設定したアナライザー名に合わせてください。

### 動作確認

「イヤフォン」で検索して、商品名が「イヤホン」の商品1がヒットすれば成功です。

```json
GET /products/_search
{
  "query": { "match": { "name": "イヤフォン" } }
}
```

「PC」で検索すると `パソコン` に展開され、商品2「ノートパソコン」がヒットします（`ノートパソコン` は kuromoji で `ノート`＋`パソコン` に分割されるため、`パソコン` トークンに一致）。

```json
GET /products/_search
{
  "query": { "match": { "name": "PC" } }
}
```

## 9.7　Synonyms API で辞書を管理する（9.x の推奨）

ファイル方式（`synonyms_path`）は、辞書ファイルを**全ノードに配置・同期**し、更新のたびに各インデックスで `_reload_search_analyzers` を叩く必要がありました。**Synonyms API（8.10 で導入）** はこれをAPI管理に置き換え、更新時の**自動リロード**まで面倒を見てくれます。学習用の single-node 構成でも、ファイル配布が不要でずっと手軽です。

### 作成・全体更新

```json
PUT /_synonyms/products-synonyms
{
  "synonyms_set": [
    { "id": "earphone", "synonyms": "イヤホン, イヤフォン" },
    { "id": "pc",        "synonyms": "PC => パソコン" }
  ]
}
```

- ボディ全体を送ると、そのセットは**丸ごと置き換え**られます。
- 作成・更新時、`updateable: true` で参照している検索アナライザーが**自動的にリロード**されます。

### ルール単位の追加・更新

セット全体を送らず、1ルールだけ upsert できます。

```json
PUT /_synonyms/products-synonyms/speaker
{
  "synonyms": "スピーカー, スピーカ"
}
```

これで「スピーカ」でも商品5「Bluetoothスピーカー」がヒットするようになります。**再インデックスは不要**で、既存ドキュメントはそのまま、検索時展開だけが変わります。

### 取得・削除

```json
GET    /_synonyms/products-synonyms
DELETE /_synonyms/products-synonyms
```

> **削除の注意**：インデックスの検索アナライザーが参照中のセットは削除できません。先にアナライザーの参照を外してから削除します。

### 運用上の注意（コラム）

- **スコアへの影響**：シノニムを足すと語彙統計（IDF）が変わり、ランキングが動きます。辞書変更は、ランキング評価 API や A/Bテストで**変更前後を比較**してから本番へ。
- **フィルタの順序**：`lowercase` などの正規化はシノニムより前。ステマー（活用の正規化）との前後関係でも展開結果が変わるため、`_analyze` で確認する癖をつける。
- **大規模辞書と安全弁**：膨大なルールを読み込むと、Elasticsearch はサーキットブレーカーでメモリを保護します。`lenient: true` なら空辞書にフォールバックしてログに記録、`false` なら該当インデックスが red 状態になります。巨大辞書を扱うときは挙動を把握しておきましょう。

## まとめ

- シノニムは、表記ゆらぎ・略語・英語/カナの違いによる**検索の取りこぼし**を埋める。`text` フィールドにのみ効き、`keyword` には効かない。
- ルールは **equivalent（カンマ・双方向）** と **explicit（`=>`・一方向）**。混同するとランキングが壊れる。
- 複数語シノニムを正しく扱うには **synonym_graph を検索アナライザーで**使う（トークングラフはインデックスに保存できないため）。
- **検索時展開が基本**。再インデックス不要で、更新に強く、複数語も安全。インデックス時展開は安定した言語規則に限定。
- 既存インデックスへの後付けは close → settings 追加 → open → `search_analyzer` 差し替え。`search_analyzer` は既存フィールドでも更新できる。
- 辞書は **Synonyms API（`synonyms_set` ＋ `updateable: true`）** で管理すると、API から更新でき自動リロードされる。

## 理解度チェック

**Q1.** 「イヤホン, イヤフォン」と「PC => パソコン」は、それぞれどんな展開をしますか。

<details><summary>解答</summary>

- 「イヤホン, イヤフォン」は **equivalent（双方向）**。どちらの語で検索しても互いにヒットします。
- 「PC => パソコン」は **explicit（一方向）**。「PC」は「パソコン」に展開されヒットしますが、「パソコン」で検索しても「PC」には展開されません。
</details>

**Q2.** 複数語シノニム（例：`ノートパソコン, ラップトップ`）を**インデックス時**に展開すると何が問題ですか。

<details><summary>解答</summary>

複数語シノニムは正しく扱うためにトークングラフが必要ですが、Lucene のインデックスはグラフを保存できず**平坦化**されます。その結果トークンの位置がずれ、**フレーズ検索が壊れる**などの不具合が起きます。正しく扱うには `synonym_graph` を**検索アナライザー**で使います。
</details>

**Q3.** `updateable: true` を付けたシノニムフィルタには、どんな制約がありますか。

<details><summary>解答</summary>

そのフィルタを含むアナライザーは**検索アナライザーとしてしか使えません**（インデックス時には使用不可）。また `updateable` は**インライン `synonyms` では使えず**、`synonyms_path`（ファイル）か `synonyms_set`（Synonyms API）と組み合わせる必要があります。
</details>

**Q4.** 既存の `products` に検索時シノニムを後付けする手順を、順番に述べてください。

<details><summary>解答</summary>

1. （先に）Synonyms API で辞書セットを作成する
2. `POST /products/_close` でインデックスを閉じる
3. `PUT /products/_settings` でシノニムフィルタと検索アナライザーを追加する
4. `POST /products/_open` で開く
5. `PUT /products/_mapping` で `name` / `description` の `search_analyzer` を差し替える

データの再インデックスは不要です（`search_analyzer` は既存フィールドでも更新できるため）。
</details>

**Q5.** シノニム辞書に「PC」を含めたのに、大文字の「PC」で検索しても効かないことがあります。よくある原因は。

<details><summary>解答</summary>

`lowercase` フィルタが `synonym_graph` より**後ろ**にある、または無いために、「PC」と「pc」が別トークンとして扱われ辞書に一致していない可能性があります。正規化系のフィルタはシノニムより**前**に置きます。`_analyze` でトークン列を確認しましょう。
</details>

## 次章予告

第10章「**表記ゆれ対応**」では、シノニム辞書だけでは追いつかない、より機械的な揺れを扱います。全角／半角、大文字／小文字、ひらがな／カタカナ、ローマ字、そして未知語のあいまい一致です。`icu_normalizer` や `icu_folding`（第2章で導入した icu プラグイン）、`kuromoji_readingform`（読み・ローマ字化）、そして n-gram による部分一致を組み合わせ、「辞書に載っていない揺れ」を吸収する設計を、`products` インデックスで組み立てます。シノニム（辞書で明示）と正規化（規則で機械的に）の**役割分担**を意識すると、両者はきれいに補完し合います。
